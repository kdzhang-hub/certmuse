# 首次诊断改为可选自我诊断改造方案 V1

> 状态：待评审，尚未实施
> 依据：《软考学习业务全流程业务流程与规则 V1》第 9、10 节
> 影响范围：学员端、学习目标/首页分流、诊断服务、题集发布、画像结算、数据库、Mock 与自动化测试
> 不在本次直接修改范围：每日任务、专项练习、真题、模拟考试的具体选题和评分规则

## 1. 改造结论

当前代码和《首次诊断业务与交互规则 V1.0》《U04-U06 首次诊断后端接口契约 V1》实现的是**固定 50 题、完成前不可进入正常学习首页**的“首次诊断”。这与全流程 V1 的现行口径冲突：诊断应为用户建立目标后的**可选自我诊断**，可选择简单、中级或详细档，也可完全跳过；学习、画像和准备度不能被一次诊断解锁或决定。

本次改造采用下面的目标模型：

```text
登录 → 设置有效目标 → 学习首页
                         ├─ 不诊断：直接做任务/专项练习/真题等，逐步形成画像
                         ├─ 发起自我诊断：选择简单/中级/详细 → 作答 → 报告/画像更新
                         └─ 已有未完成诊断：可继续，也可暂不继续学习
```

“首次”只表示该目标下历史上第一份诊断，不再是产品流程状态或数据模型的前提。新建会话、题集、报告和证据统一使用 `self_diagnosis` / `SELF_DIAGNOSTIC` 语义；历史 `initial_diagnosis` 数据只读保留，不做改写。

## 2. 当前实现与目标规则的差异

| 现状 | 证据位置 | 目标改动 |
| --- | --- | --- |
| 建立目标后返回 `START_DIAGNOSTIC`，无会话也强制进入诊断说明 | `LearningGoalServiceImpl.result`、`OnboardingServiceImpl.status` | 建立目标后返回 `ENTER_HOME`；没有诊断不再属于阻断状态。 |
| 路由守卫把“请先完成首次诊断”作为提示和分流依据 | `web/student/src/permission.ts` | 删除诊断完成门槛；只保留“目标不存在”到目标设置页的分流。 |
| 首页只要诊断未开始/进行中就替换为首次诊断卡 | `views/student/dashboard/index.vue` | 首页正常展示学习入口；未开始显示可关闭/可稍后处理的可选 CTA，进行中显示“继续诊断”但不替换任务与题库。 |
| 前端和后端将题量写死为 50 | `diagnostics.ts`、`session.vue`、`DiagnosticServiceImpl.TOTAL`、计时 BO、SQL 约束 | 全部以会话冻结的 `totalCount` 为准；题量由所选档位的发布题集决定。 |
| 仅允许 `FIRST_DIAGNOSTIC` 题集，且发布必须恰好 50 个选择题、覆盖三个科目 | `CollectionServiceImpl`、`DiagnosticMapper.xml` | 新增 `SELF_DIAGNOSTIC` 题集及档位配置；按档位规定覆盖、题型和题量，不再把 50 题和全科覆盖写成通用前提。 |
| 每目标只能有一份活动 `initial_diagnosis`，且没有用户放弃接口 | `20260812_add-initial-diagnostic.sql`、`DiagnosticServiceImpl` | 每目标最多一份进行中自我诊断；允许显式放弃，放弃不结算报告、画像、错题。之后可重新选任意档创建新会话。 |
| 完成诊断被当作“初始画像”的唯一来源 | 首次诊断规则文档、`DiagnosticResultDispatcher` | 自我诊断只是证据来源之一；任务、练习、真题、模拟和独立验证使用统一证据规则。没有证据的知识点保持 `UNKNOWN`，不能初始化默认分数。 |

## 3. 必须先确认的业务边界

以下内容是后端开始编码前的产品确认项。未确认时不得用 50 题、50 分钟或仅选择题作默认替代。

1. 每个资格、考纲版本、档位的实际题量、预计时长、科目覆盖、题型配比和最低知识点覆盖要求。全流程 V1 只规定“开始前展示”，未给出数值。
2. 中级、详细档包含主观题时的评分能力是否已可用。未具备可信主观题评分时，发布校验必须阻断该档位，不能把主观题静默替换为选择题。
3. 用户“放弃”的含义：本方案定义为不结算任何结果，并保留会话仅供历史审计；用户可立刻创建另一档诊断。
4. 允许同一目标存在的历史已完成诊断数量：本方案允许多份，首页默认展示最新完成报告；学习记录保留全部历史。

## 4. 目标业务规则与状态机

### 4.1 分流规则

- 无有效目标：`nextAction = SET_GOAL`，所有产生学习记录的能力均要求先创建目标。
- 有有效目标且没有诊断：`nextAction = ENTER_HOME`。首页可显示“了解当前基础”入口；题集不可用时只禁用该入口，不影响学习。
- 有进行中诊断：`nextAction = ENTER_HOME`，并返回 `activeDiagnostic` 摘要。用户直接访问诊断页时恢复该会话；首页、专项练习、真题等仍可访问。
- 已交卷处理、完成、失败：均不改变首页入口；对应报告/结果页仅由诊断详情链接、学习记录或首页的非阻断提示打开。
- 目标暂停、取消、完成的既有限制继续生效；进行中诊断按目标状态规则处理，不得通过诊断绕过目标约束。

### 4.2 会话状态

```text
NOT_CREATED --开始所选档--> IN_PROGRESS --交卷--> PROCESSING --> COMPLETED
                                  |                 |                 |
                                  |                 +--> FAILED ------+--重试结果-->
                                  +--放弃--> ABANDONED
```

- `ABANDONED` 是终态：保留题目快照、已保存答案和审计，但不产生报告、画像、错题或学习证据。
- `IN_PROGRESS` 仍保持断点恢复、最后一次答案、并发版本、请求幂等和多设备计时租约等现有保障。
- 用户未答完可以交卷；报告分别展示“未作答”和“本档未覆盖”范围。未作答不伪造为错误答案。
- 每次新建会话冻结：目标、资格、考纲版本、题集修订、档位、总题数、预计时长、题目顺序、规则版本。后续题集或规则发布不能改写历史。

### 4.3 档位与题集

档位是可配置内容，不由前端推断：

| 档位 | 面向用户的定位 | 最低发布要求 |
| --- | --- | --- |
| `SIMPLE` | 快速了解核心科目和关键知识点，以客观题为主 | 覆盖配置的核心范围；允许只含客观题。 |
| `STANDARD` | 扩大科目和知识点覆盖，可包含主观题 | 满足配置的扩大范围和题型配比。 |
| `DETAILED` | 覆盖所有主要科目和更多关键知识点，增加主观题比例 | 覆盖配置的全部主要范围；满足主观题比例与评分可用性。 |

名称可在配置中显示为“简单 / 中级 / 详细”，枚举采用 `SIMPLE`、`STANDARD`、`DETAILED`。所有数量、时长和覆盖规则均由题集修订快照返回，客户端只展示，不计算或补题。

3. 为兼容已上线客户端，保留 `diagnosticStatus` 字段，但补充可选 `activeDiagnostic`：

```ts
interface ActiveDiagnosticSummary {
  sessionId: string;
  level: 'SIMPLE' | 'STANDARD' | 'DETAILED';
  status: 'IN_PROGRESS' | 'PROCESSING' | 'COMPLETED' | 'FAILED';

interface OnboardingStatusV2 {
  goalStatus: 'NONE' | 'ACTIVE' | 'PAUSED';
  nextAction: 'SET_GOAL' | 'ENTER_HOME' | 'CONTACT_SUPPORT';

```

4. 不再由 onboarding 返回 `START_DIAGNOSTIC`、`CONTINUE_DIAGNOSTIC`、`WAIT_PROCESSING` 等页面命令。诊断详情的状态分流归诊断 API 所有，避免一个“nextAction”同时承担登录入口和会话恢复。

### 5.2 自我诊断 API V2

不要直接把现有 V1 的 `questionCount: 50` 改成普通 number 后无版本发布；这会让旧客户端对会话、题号和计时产生错误解释。新增 V2 路径，旧 V1 仅服务旧 `initial_diagnosis` 历史会话，停止用于新建。

| 接口 | 行为 |
| --- | --- |
| `GET /api/assessment/self-diagnostics/preflight` | 返回当前目标、活动会话（若有）和所有已发布、可用档位。题集缺失只体现在该档位 `available=false`，整体请求仍成功。 |
| `POST /api/assessment/self-diagnostics/sessions` | 请求 `{ diagnosticRevisionId, goalVersion }`；校验所选修订仍为该目标可用的 `SELF_DIAGNOSTIC` 档位，幂等创建或恢复同一进行中会话。 |
| `GET /api/assessment/self-diagnostics/{sessionId}` | 返回会话的动态 `totalCount`、档位、冻结预计时间、进度、导航和状态。 |
| `PUT /.../{sessionId}/items/{order}/draft`、`POST /pause`、`GET /finish-check`、`POST /finish`、计时、状态、重试、报告 | 沿用 V1 的安全语义，但以会话总题数校验题序；只接受拥有的 `self_diagnosis` 会话。 |
| `POST /.../{sessionId}/abandon` | 仅 `IN_PROGRESS` 可调用；写入放弃原因枚举 `USER_ABANDONED`、关闭租约、状态迁移到 `abandoned`，不创建异步结算任务。 |

预检核心响应：

```ts
interface SelfDiagnosticPreflightVo {
  goal: GoalSnapshot;
  activeSession: ActiveDiagnosticSummary | null;
  options: Array<{
    revisionId: string;
    level: 'SIMPLE' | 'STANDARD' | 'DETAILED';
    displayName: string;
    questionCount: number;
    estimatedMinutes: number | null;
    subjectBreakdown: Array<{ examSubjectId: string; subjectName: string; questionCount: number }>;
    questionTypeBreakdown: Array<{ questionType: 'CHOICE' | 'CASE' | 'ESSAY'; questionCount: number }>;
    coverageSummary: string;
    available: boolean;
    blockers: Array<{ code: string; message: string }>;
  }>;
}
```

请求和响应继续遵守当前的 `R<T>`、`X-Request-Id`、资源归属、409 状态冲突、脱敏错误与服务端计时原则。前端不能上传总分、证据、画像分数或客户端用时。

### 5.3 诊断服务与 Mapper

**主要修改文件**

**具体改动**

1. 新建 `SelfDiagnosticService` / `SelfDiagnosticController`，不要继续扩张名为“首次诊断”的公共 API。可提炼现有保存、计时、交卷、幂等公共逻辑，但不得让 V2 查询误读 V1 会话。
2. 删除 `DiagnosticServiceImpl.TOTAL`、`checkOrder(1..50)`、`revisionVo(...TOTAL...)`、`startFrom(...TOTAL...)` 等固定常量；从冻结的 `cm_session_question` 数量或会话快照读取总题数。

5. 为“每目标最多一份进行中自我诊断”保留唯一索引；`submitted/settling` 不应阻止用户开始新的诊断，因为已交卷会话已不可编辑。若产品要求处理期间只能等待，需在第 3 节明确后再扩大唯一范围。
6. `abandon` 走受控状态迁移，记录操作者、时间、原因和 `traceId`；不可删除答卷、题目快照或幂等记录。
7. 保持交卷后不可改、重复交卷只结算一次、结果失败可重试、断点恢复、会话版本冲突和单活动计时租约等 V1 已实现能力。

### 5.5 画像、证据与报告

**主要修改文件**

- `assessment/support/DiagnosticResultDispatcher.java`
- `assessment/support/DiagnosticProfileRules.java`
- `DiagnosticMapper.xml` 中 `insertReport`、`upsertKnowledgeProfile`、`insertEvidence` 等语句

**改动**

1. 新会话的 `source_type` / `report_type` 使用 `self_diagnosis`；保留 `initial_diagnosis` 供历史展示和审计。
2. 去掉“首次诊断初始化基线”的特权分支。新诊断与每日正式作答、专项练习、真题、模拟、独立验证进入同一证据聚合规则，差异只由题目新旧、提示、时间、可信度、覆盖和规则版本决定。
3. 不能把未覆盖知识点写入 `cm_knowledge_profile` 的默认 0 分或中间值；报告和画像返回 `UNKNOWN` / “未评估”。
4. 重测优先从用户未作答题或等价新题选取；若内容不足而复用，保存 `is_retest=true`（或等价冻结字段），由规则降低证据作用并在报告说明。该字段不能只存在前端。
5. 报告增加档位、实际题量、预计/有效时长、已答/未答、覆盖范围、未覆盖范围、知识点状态/可信度、画像变化原因和完整解析入口；不输出内部权重或演算参数。
6. 仅在会话成功交卷并完成可信评分后写证据、错题和报告。`ABANDONED`、不可用题、未可信评分的主观题均不得结算；部分完成时按全流程 V1 的部分结果规则显示。

### 5.6 数据库迁移与兼容

新迁移必须新建有序 SQL 文件，不修改已部署的 `20260812_add-initial-diagnostic.sql` 或基础约束。

1. 扩展 `cm_learning_session.session_type` 约束，新增 `self_diagnosis`；保留 `initial_diagnosis`。
2. 添加 `cm_learning_session.diagnostic_level`（仅 `self_diagnosis` 非空）与 `diagnostic_abandoned_reason`（仅 `abandoned` 非空），并增加 `abandoned` 到状态检查、状态转换函数和审计验证。
3. 将仅对 `initial_diagnosis` 的 `last_question_order BETWEEN 1 AND 50` 检查改为：旧类型仍保留 1..50，新类型为 `>= 1`；服务层负责上限。迁移前先验证已有行，使用 `NOT VALID` 后再在维护窗口 `VALIDATE CONSTRAINT`。
4. 创建 `uk_cm_learning_session_active_self_diagnosis`：`(user_id, goal_id)`、`session_type='self_diagnosis' AND status='in_progress'`；保留旧索引直到旧 V1 API 下线。
5. 扩展 `cm_collection`/导入相关 `collection_type` 检查和 `cm_collection_current.purpose_code` 允许集合，新增 `SELF_DIAGNOSTIC` 与档位列/唯一索引。
6. 修改 `cm_diagnostic_timer_lease` 的题序检查为 `question_order >= 1`。不允许按会话动态写 CHECK；题序上限交由业务查询验证。
7. 报告、证据、异步 job 的枚举/检查若有限制，分别追加 `self_diagnosis`，不得更新历史 `initial_diagnosis` 行。
8. 更新 `verify_local.sql`：同时验证新会话唯一索引、新约束、档位唯一发布、计时租约约束与旧迁移仍可通过。

回滚策略：先下线 V2 新建入口，再禁用 `SELF_DIAGNOSTIC` 发布修订；已创建会话继续使用已冻结快照完成或放弃。不得删除新会话或将其改回 `initial_diagnosis`。数据库约束迁移只做向前兼容扩展，确认无 V2 会话后才可在独立变更中收紧。

3. 首页始终加载任务、题库与画像摘要。画像无证据时显示“尚无作答证据；可从今日学习或自我诊断开始”，不显示默认分数。
4. 有进行中诊断时，首页显示轻量卡片“有一份简单/中级/详细诊断待继续，已完成 X/Y 题”，提供“继续”“暂不继续”；不得遮蔽今日任务。
5. 有处理/失败/完成会话时显示“查看结果/重试结果/查看最新报告”链接，不强制跳转。历史报告从学习记录进入。

### 6.2 API 类型、Mock 与页面

**修改文件**

- `web/student/src/api/certmuse/learning/diagnostics.ts`（建议新建 `self-diagnostics.ts`，旧文件仅保留 V1 兼容）

2. 若有进行中会话，说明页不允许另建，展示恢复提示和“继续上次诊断”；用户必须先继续或放弃。该限制防止同一目标同时产生两份可编辑会话。

7. Mock 必须模拟三个可用性状态、动态题量、放弃、重测、处理中、失败重试和无诊断直接学习；删除所有“固定 50 题即可证明闭环”的断言。

### 6.3 可访问性与错误处理

- 档位卡用文字说明，不只用颜色区分可用/不可用。
- 缺某档位时明确原因和下一步（例如“详细档题集暂未发布”），不得把服务错误包装成用户能力问题。
- 网络中断、保存失败、会话版本冲突、计时租约被替换、交卷结果不确定均沿用现有 V1 交互；页面恢复时必须重新读取服务端会话，不信任本地题量或计时。
- 旧 `/learning/diagnostic/**` 仅在仍存在 V1 历史会话时保留只读/兼容入口；新 CTA 不得再指向它。下线前在路由层明确提示“这是历史诊断记录”。

## 8. 实施顺序与发布策略

1. **规则冻结**：确认第 3 节四项业务参数；批准 V2 契约和新枚举，不先改前端文案。
2. **内容与数据能力**：完成数据库向前兼容迁移、管理端档位发布校验，至少发布一个真正符合规则的 `SIMPLE` 档位；三个档位未齐时允许部分可用。
3. **后端 V2**：实现 V2 预检、创建/恢复、动态题数、放弃、报告与统一证据结算；保留 V1 只读兼容。
4. **学员端 V2**：移除诊断守卫，接入可选入口和 V2 页面；同步完善 Mock。
5. **灰度**：通过 feature flag（例如 `selfDiagnosticV2Enabled`）仅对内部账号开放；比较 V1 历史读取与 V2 新建、结算、回滚行为。
6. **全量**：打开 V2，新建目标默认进入首页；停止创建 V1 会话，保留 V1 历史查询至少一个明确版本周期。
7. **清理（单独变更）**：确认无可恢复 V1 会话和兼容客户端后，再下线 V1 创建接口、旧路由和 `FIRST_DIAGNOSTIC` 发布入口；历史报表按只读迁移策略保留。

## 9. 验收清单

### 必测主链路

1. 新用户创建目标后直接进入首页，可开始专项练习；没有诊断不会被重定向，也不会生成默认画像。
2. 用户分别选择简单、中级、详细档，开始页展示的题量、题型、覆盖和预计时长与会话快照一致。
3. 某档题集不可用时，该档说明原因，另两档和不诊断学习路径正常可用。
4. 同一目标有进行中诊断时可从首页恢复；用户仍可完成其它学习行为；不能再创建第二份进行中会话。
5. 保存、暂停、刷新、断网、换设备、并发编辑、重复交卷、结果失败重试的 V1 保障在动态题量下均成立。
6. 放弃会话后没有报告、画像变化、错题或学习证据；用户可重新创建任意档位。
7. 提前交卷报告同时展示未答题数与未覆盖知识点；两者不混淆。
8. 重测优先新题；被迫复用题在服务端记录并降低证据作用。
9. 不做任何诊断，只通过正式练习等有效证据也能得到逐步更新的画像和准备度；未评估点不显示为零分。
10. 历史 `initial_diagnosis` 报告可读、不可改，新 V2 不会向其中重复写证据或报告。

### 回归与质量门禁

- 后端：为 Onboarding 分流、档位发布、动态题量边界、放弃、幂等、状态迁移、V1 历史隔离、统一证据聚合新增聚焦 JUnit 测试；运行 CertMuse 模块测试。
- 前端：更新 `permission.spec.ts`、`onboarding-routing.spec.ts`、诊断页面单测和 Mock 测试；覆盖 10/非 50 题、未答交卷、放弃、无诊断首页和旧会话链接。
- 数据库：在空库、含 V1 历史会话库、含进行中 V1 会话库执行迁移验证和 `verify_local.sql`；不得删除或改写历史答卷。
- 发布前：用真实已发布题集抽样确认题目/知识点/评分点可用。题集显示“已发布”不等于诊断质量已验证。

## 10. 不做的事情

- 不把诊断总分作为通过考试的承诺或唯一准备度结论。
- 不因为用户未诊断而填充伪造能力分、薄弱项、学习任务或模拟报告。
- 不在客户端计算或上传画像、评分、证据权重、总用时。
- 不自动把旧 50 题选择题题集转换为“详细档”。
- 不删除、重置或强行完成正在进行的历史首次诊断；历史数据只读兼容后再按独立计划下线。
