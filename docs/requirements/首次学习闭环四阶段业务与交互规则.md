## 1. 文档目的与完成口径

本文是团队实施和联合验收依据，把“首次流程收口—初始画像落地—学习计划生成—每日任务闭环”串成一条可开发、可联调、可恢复、可测试的业务链路。团队应使用本文统一范围、状态、用户去向、异常恢复和阶段出口，再分别形成接口契约、页面实现、测试用例与验收记录。本文不替代已经冻结的接口契约、画像计算规范或数据库设计。

四阶段必须顺序衔接，但“进入下一阶段”不等于上一阶段的所有后台工作都已完成。系统只能依据服务端状态决定用户去向，不能根据前端缓存、页面访问记录或 `firstLogin` 单独推断流程完成。

| 阶段 | 输入 | 阶段出口 | 当前依据 |
|---|---|---|---|
| 1. 首次流程收口 | 身份、学习目标、诊断状态 | 用户进入诊断报告或安全的后续入口 | 已有需求、接口与代码 |
| 2. 初始画像落地 | 冻结诊断作答、评分及知识点映射 | 生成可解释、可追溯的初始画像 | 已有 V8 规则，工程闭环待验收 |
| 3. 学习计划生成 | 有效目标、初始画像、可用学习时间 | 生成可执行的阶段计划和周计划 | 待评审业务基线 |
| 4. 每日任务闭环 | 当前计划、画像、历史完成情况 | 今日任务完成并回写进度和画像证据 | 待评审业务基线；当前页面主要为 Mock |

## 2. 统一业务原则

1. 服务端状态是唯一流程事实源。刷新、重新登录、直接访问 URL 和换设备都必须恢复到同一业务步骤。
2. 诊断报告分、知识点画像分和计划优先级是三类不同数据，不得互相替代。
3. 没有证据时显示“未评估”，不能补成 `0`、`50` 或虚构结论。
4. 计划和任务只能引用有效资格、有效题目修订、有效知识点及当前画像；生成时必须冻结关键输入版本。
5. 自动重试必须幂等。失败恢复不得重复创建诊断、画像证据、学习计划或每日任务。
6. 用户可以看到“为什么这样安排”的业务解释，但不展示内部公式、权重或不稳定的算法细节。
7. 目标暂停时不生成新任务；已有未完成诊断保留进度。恢复目标后从服务端状态继续。
8. 功能状态必须区分“已设计、已实现、已测试、已部署”，不得以本文存在作为实现完成证明。
9. 学习安排的业务优先级固定为“先补全画像，再补弱”：先用验证类任务补齐覆盖、可信度和冲突结论，再对已有充分负向证据的知识点安排补弱。未评估或低可信度不得直接等同于薄弱。

## 3. 阶段一：首次流程收口

### 3.1 业务目标

让新用户、首次流程中断用户和更换考试资格后需要重新诊断的用户，都能稳定进入唯一正确步骤：设置目标、开始诊断、继续诊断、等待处理、查看报告或进入首页。

### 3.2 状态决策规则

| 业务状态 | 用户去向 | 关键规则 |
|---|---|---|
| 无有效学习目标 | 设置学习目标 | 不允许绕过目标设置进入诊断或首页 |
| 目标有效、诊断未开始 | 诊断说明页 | 展示题量、预计时间、保存与恢复规则 |
| 诊断进行中 | 恢复原诊断 | 不新建第二份诊断；恢复服务端保存的题目位置和答案 |
| 已交卷、结果处理中 | 处理状态页 | 允许刷新或离开；禁止重复交卷 |
| 结果处理失败且可重试 | 失败恢复页 | 复用原会话、最终答案和冻结快照，只重试失败阶段 |
| 诊断与必要产物完成 | 报告或首页 | 首次完成优先展示报告；再次登录可进入首页 |
| 目标暂停 | 暂停说明或首页 | 不创建新任务；诊断进度不得丢失 |
| 状态未知或互相矛盾 | 安全错误页 | 不默认放行到首页，提供重试和联系支持入口 |

`firstLogin=false` 不能证明首次流程完成。前端只消费服务端 `nextAction` 并映射到本地受控路由，不能执行服务端返回的任意字符串路径。

### 3.3 交互流程

1. 登录成功后，客户端请求首次流程状态并显示加载态，避免先闪现首页。
2. 无目标时进入目标设置页。用户选择考试资格、考试日期和每日可用时间；提交前展示摘要并校验资格有效、日期合理、时间范围有效。
3. 目标创建成功后进入诊断说明页，不直接自动开始计时。用户点击“开始诊断”后才创建或恢复会话。
4. 答题页显示当前题号、总题量、已答数量和保存状态。切题前提交本题草稿；保存失败时保留本地答案并明确提示重试。
5. 用户主动暂停时等待在途保存完成，再记录当前位置。关闭页面、会话过期或换设备后仍从服务端状态恢复。
6. 交卷前执行完成检查：有未答题时明确列出；存在本地或服务端未完成保存时禁止交卷。
7. 确认交卷后按钮立即进入处理中，重复点击只返回原结果。网络结果不明确时先查询会话状态，不能再次创建交卷事实。
8. 后台评分、报告、画像或后续产物生成期间显示处理状态。失败时只在服务端允许的情况下展示“重试生成”。
9. 报告可用后进入报告页；报告页提供明确的下一步入口，不把用户留在无出口页面。

### 3.4 异常和恢复

- 多标签页或多设备同时操作时，以服务端版本和首次有效提交为准；冲突页面重新拉取最新状态。
- 登录过期时保存可恢复的本地草稿，重新认证后先读取服务端版本，再决定是否补交。
- 题目无法呈现或无法评分时标记为无效题，不得生成伤害用户画像的证据。
- 未知 `nextAction`、会话不属于当前用户、资格失效或数据版本缺失时进入安全错误态并记录可追踪错误编号。

### 3.5 阶段出口与验收

- 新用户可完成“登录—目标—诊断—报告”。
- 在目标设置、答题、交卷处理三个位置中断后，重新登录均恢复到正确位置。
- 重复开始、重复保存、重复交卷和结果重试不会产生重复业务事实。
- 未完成首次流程时，刷新和直接访问学习首页不能绕过流程。
- 阶段出口由真实服务端状态证明，不以 Mock 页面可操作作为完成。

## 4. 阶段二：初始画像落地

### 4.1 业务目标

把首次诊断中的有效作答转换为叶子知识点暂定能力、可信度、覆盖率、科目总览、优先学习方向和初始总画像。诊断报告回答“这次答得怎样”，画像回答“当前有哪些可用学习证据”，两者必须分别保存和解释。

### 4.2 证据准入规则

1. 只使用冻结题目修订、有效评分事实和明确的评分点—叶子知识点映射。
2. 一道题可影响多个明确映射的叶子知识点，但不得通过标题相似度自行推断映射。
3. 无有效知识点映射的题目只进入诊断报告，不进入画像和覆盖率。
4. 未正常呈现、无法评分或作答过程无效的题目不生成画像证据。
5. 答案有效但计时链缺失时保留答题证据，时间系数按中性处理，不施加超时惩罚。
6. 正常留空按错误或零得分率处理；系统无效题不能按用户错误处理。
7. 首次诊断只形成初始或暂定画像，单题不得直接判定知识点已掌握。
8. 未覆盖知识点保持“未评估”，不参与虚假的平均补分。

具体分值、系数、置信度和聚合算法以《人物画像实际应用 v8》为唯一计算依据，本文不复制另一套公式。

### 4.3 生成流程

1. 交卷完成后冻结最终答案、题目、评分点、知识点映射和规则版本。
2. 完成题目评分并形成不可覆盖的评分事实；人工改判通过修订和重放处理。
3. 按“作答 × 叶子知识点”生成当前有效证据，保证幂等。
4. 聚合每个已覆盖叶子知识点的暂定能力、可信度、不同题数量、证据状态和作答效率。
5. 仅从有效叶子画像向上聚合科目总览和初始总画像；父级结果不得反向修改叶子。
6. 计算资格范围内覆盖率、核心知识点覆盖情况、数据充分度和优先学习方向。
7. 保存诊断报告与画像投影，并记录规则版本、输入快照、生成时间和失败阶段。
8. 全部必要产物可读后才标记画像可用。局部失败进入可重试状态，不要求用户重答。

### 4.4 报告与画像交互

- 报告顶部展示诊断完成时间、题量、已答/未答、正确率或实际得分。
- 分科区域展示各科表现及数据充分度，不用少量题目夸大稳定结论。
- 知识点区域只展示有证据的知识点；未覆盖范围单独说明“尚未评估”。
- 每个结论至少包含状态、简短依据和下一步建议，例如“需要加强：本次两道有效题均未答对”。
- 初始总画像必须标注“初始/暂定”，不得在覆盖率或可信度不足时给出正式通过把握。
- 用户可以从报告进入学习计划说明；处理失败时看到失败阶段的通俗说明和允许的恢复动作。

### 4.5 阶段出口与验收

- 全对、全错、部分正确和未覆盖知识点均产生符合 V8 规则的唯一结果。
- 报告分不能直接写成知识点分；无映射题不能污染画像。
- 可追溯任一画像结论使用的作答、映射快照和规则版本。
- 重试、并发与迟到评分不会重复累计证据，最终结果可确定性重算。
- 页面不展示虚假知识点、固定薄弱项、默认分或 Mock 结论。

## 5. 阶段三：学习计划生成（待评审业务基线）

### 5.1 业务目标

根据用户有效目标、距离考试时间、每日可用时间和初始画像，生成“阶段计划 + 当前周计划”。计划用于确定学习方向和节奏，不直接等同于每天的题目清单。

### 5.2 计划输入与前置条件

生成前必须具备：有效资格及版本、有效考试日期、每日可用分钟、可用画像或明确的数据不足状态、可用学习内容和题目。缺少任何强制输入时不得生成伪计划，应引导用户补充目标、等待画像或提示内容不足。

画像覆盖不足不阻止生成基础计划，但计划必须安排补测或探索性任务，并标记这些安排是为了补充证据，不能把未评估知识点当成薄弱知识点。

### 5.3 计划规则

1. 计划范围以当前学习目标为边界。切换资格时旧计划停止新增任务并保留历史，新目标重新生成计划。
2. 阶段划分至少包含基础补齐、重点强化、综合检验和考前巩固；阶段长度由剩余日期和可用时间决定，不固定平均分配。
3. 计划先判断画像是否完整可用，再判断能力强弱。画像完整性包括知识点覆盖、直接证据数量、可信度、新鲜度和未解决冲突。
4. 第一优先级是补全画像：对未评估、低可信度、证据过期或存在冲突的知识点安排验证类任务。验证顺序再综合知识点重要度、考试临近程度、覆盖缺口和先修关系确定。
5. 第二优先级是补弱：只有知识点已有充分、有效且一致的负向证据，能够确认其为真实薄弱项时，才安排知识学习、专项练习或订正任务。不得把“没有数据”当作“能力差”。
6. 同时存在画像缺口和已确认薄弱项时，计划容量优先保障验证类任务；补弱任务使用剩余容量。阻断后续作答或存在数据安全风险的先修问题可以作为例外提前处理，并记录原因。
7. 周计划总时长不得超过用户声明的可用时间。预留复习、补测和未完成缓冲，不能把全部时间填满。
8. 少量任务未完成时不自动无限堆积。系统在下一次滚动生成时重新排序、延期或替换，并说明影响。
9. 用户修改考试日期或每日时间后，先展示变化影响，再确认重排；已完成记录不变，进行中任务原则上保留到当日结束。
10. 计划生成必须保存画像版本、规则版本和内容版本，使“为什么安排”可解释且可重现。

### 5.4 交互流程

1. 用户从诊断报告点击“查看学习计划”，进入计划生成说明页。
2. 页面回显考试资格、考试日期、每日时间和画像摘要。用户可返回修改目标，但不能直接编辑系统画像。
3. 点击“生成计划”后显示处理态；重复点击返回同一生成任务。
4. 生成完成后先展示计划摘要：剩余周数、四类阶段、当前阶段目标、本周重点、计划分钟和安排依据。
5. 用户确认后计划生效并进入首页。若用户暂不确认，保留草案，不生成正式每日任务。
6. 输入变化或画像发生显著更新时提示“计划可更新”，说明变化原因；普通小幅画像变化通过下一周滚动计划吸收，避免频繁打扰。
7. 生成失败时保留输入并允许重试；内容不足时明确列出缺失科目或知识点，不展示空白成功页。

### 5.5 状态建议

计划至少区分：`DRAFT`（待确认）、`ACTIVE`（执行中）、`PAUSED`（目标暂停）、`SUPERSEDED`（已被新计划替代）、`COMPLETED`（计划周期结束）和 `FAILED`（生成失败）。同一用户同一目标只能有一个生效计划。

### 5.6 阶段出口与验收

- 有充分画像和画像不足两类用户都能得到合理、可解释但不虚构的计划。
- 画像不足时验证类任务排在补弱任务之前；只有已有充分负向证据的知识点才能被标记并安排为补弱。
- 总时长不超过用户可用时间，阶段和周目标均能落到后续任务类型。
- 重复生成不产生多个生效计划；目标变更后历史与新计划边界清楚。
- 用户能理解本周重点、预计投入和安排原因，并能确认后进入首页。

## 6. 阶段四：每日任务闭环（待评审业务基线）

### 6.1 业务目标

每天把当前周计划转换为少量、明确、可完成的任务，让用户知道“今天先做什么”，并把真实完成结果回写到计划进度与画像证据。

### 6.2 每日任务生成规则

1. 只为 `ACTIVE` 目标和计划生成新任务；暂停目标不生成。
2. 每日任务总预计时长不得超过当日可用分钟，默认保留机动时间。
3. 任务来源可包括知识学习、每日练习、错题订正、间隔复习和正式验证；同一次作答只能属于一种行为类型。
4. 每日排序遵循两级主序：第一优先为画像验证，包括未评估、低可信度、证据过期和冲突待复核；第二优先为已有充分负向证据的补弱任务。一般巩固排在两者之后。
5. 验证类任务内部优先核心知识点、长期未评估、冲突待复核和临近考试仍缺证据的知识点；不得因缺少画像数据直接生成补弱结论。
6. 补弱类任务只面向已确认薄弱项，并根据重要度、薄弱程度、先修阻断和到期复习排序。推荐理由必须说明“基于哪些有效证据确认需要加强”。
7. 同一知识点和同一原题变式不得通过重复安排虚增题量、可信度或画像提升。
8. 昨日未完成任务不直接全量顺延。系统结合今天容量和优先级决定继续、延期、缩减或替换。
9. 每项任务必须包含标题、类型、知识点、预计时长或题量、推荐原因、状态和来源计划。验证任务的理由说明要补齐的画像缺口；补弱任务的理由说明已有的薄弱证据。
10. 同一用户、目标和日期只能有一份当前任务清单；重复刷新或生成必须返回原清单或显式的新修订。

### 6.3 首页与任务列表交互

- 首页首先展示今日优先任务、预计分钟、待完成数量、需要回顾数量和本周进度。
- 推荐原因默认收起，用户展开后看到简短业务理由，不展示算法权重。
- 任务状态至少包括“待开始、进行中、已完成”；不能仅靠前端点击改为完成。
- “开始学习”创建或恢复唯一会话；已有进行中任务时按钮显示“继续答题”。
- 任务列表允许按状态查看，但不鼓励用户通过频繁手工排序规避计划优先级。
- 今日全部完成时显示完成反馈和学习进度入口，不自动追加无上限任务。

### 6.4 任务执行、暂停与完成

1. 进入任务详情时展示目标、题量/内容、预计时间和完成条件。
2. 开始后创建会话并冻结题目、知识点映射、计划来源和画像入场版本。
3. 答题保存、离开恢复和重复提交遵循与诊断一致的幂等原则。
4. 暂停时保存当前位置，任务变为进行中；换设备后恢复同一会话。
5. 交卷或完成学习内容后，服务端结算会话。处理期间显示处理中，不提前计为已完成。
6. 结算成功后任务变为已完成，记录实际投入、完成时间和结果摘要；计划进度按已确认事实更新。
7. 每日任务和任务测试按 V8 批量结算画像；自主练习按单题规则更新。错题订正必须保留待验证闭环。
8. 结算失败时任务保持可恢复状态，只重试失败阶段，不要求用户重新完成已经提交的内容。

### 6.5 跨日与计划调整

- 日期切换时，已完成任务进入历史；进行中任务保留并由新一天清单明确标记“继续完成”。
- 未开始任务可由新修订替换，但必须保留原安排历史和替换原因。
- 当日实际投入低于计划时，下一日只能在容量范围内重排，不使用惩罚性文案或无限补课。
- 画像发生显著变化、题目失效或计划被替代时，未开始任务可以取消或换题；进行中会话仍按冻结快照完成，除非存在数据安全问题。

### 6.6 阶段出口与验收

- 首页能基于真实接口展示今日任务，不依赖 Mock 数据。
- 开始、暂停、恢复、完成、跨日和失败重试均不会重复创建会话或重复结算。
- 任务完成后，今日进度、周计划进度、学习历史和画像证据保持一致。
- 未完成任务不会无限堆积，目标暂停后不会继续生成任务。
- 同时存在画像缺口和已确认薄弱项时，任务清单按“验证补画像在前、补弱在后”排序；未评估项不会被错误标为薄弱。
- 用户能够从任务解释中理解安排原因，并看到完成后的下一步。

## 7. 四阶段端到端交互

```text
登录
  → 查询服务端首次流程状态
  → 设置或确认学习目标
  → 开始/恢复首次诊断
  → 交卷并等待评分
  → 生成诊断报告与初始画像
  → 查看报告
  → 生成并确认学习计划
  → 首页展示今日任务
  → 开始/恢复任务
  → 完成并结算
  → 回写计划进度与画像
  → 下一日或下一周滚动调整
```

任何节点失败都应停留在最近一个可确认状态，通过幂等重试继续；不得回退为重新注册、重新诊断或重复完成已提交任务。

## 8. 产品经理职责边界

李亚鸿在本项目中的角色为“产品经理”。产品经理面向团队提供统一的产品目标、范围、业务规则、交互要求和产品验收标准，但不承担团队分工或项目管理职责。

| 负责事项 | 具体产出 |
|---|---|
| 业务规则解释 | 确认状态含义、用户去向、计划优先级原则和任务完成口径 |
| 交互说明确认 | 确认关键页面信息、按钮动作、提示文案、异常恢复和下一步入口 |
| 产品范围管理 | 明确一期范围、非目标、阶段出口和需求优先级；确认范围变化 |
| 业务内容把关 | 确认资格、科目、知识点、题目与学习内容关系符合产品语义 |
| 产品验收口径 | 给出场景、预期结果和是否符合产品规则的意见 |
| 规则变更确认 | 对范围、业务规则或交互口径变化作出明确确认并维护版本记录 |
| 产品验收参与 | 参加真实链路验收，指出规则不一致、虚假结论或不可解释安排 |

以下事项不属于产品经理职责：为团队分工、指派开发任务、拆解技术任务、制定人员排期、日常进度追踪、跨端实施协调、代码实现与代码评审、自动化测试执行、环境部署、缺陷关闭管理以及最终项目验收签字。开发责任人负责技术拆分、实现和自动化测试；测试及项目责任人负责测试证据、缺陷与阻塞记录、人员分工、排期、发布协调和最终验收结论。

当实现与本文冲突、画像或任务结论无法解释、数据可能污染或验收证据不足时，产品经理可以从产品口径提出不通过意见，但不因此承担修复、人员分工、排期或发布责任。

## 9. 评审决策点与后续契约

阶段 3、4 在进入开发前必须由产品、后端、前端和测试共同确认以下决策，不得由开发实现自行隐式决定：

1. 每日可用时间是否支持按星期分别设置，以及可接受范围。
2. 学习阶段的固定名称、进入条件和退出条件。
3. 周计划滚动频率、显著画像变化阈值和是否需要用户再次确认。
4. 每日任务容量预留比例、每日最大任务数和跨日保留规则。
5. 学习内容、练习、订正、复习和验证各类任务的一期范围。
6. 哪些任务允许暂停、跳过或替换，以及这些行为如何影响计划。
7. 计划生成、每日任务和结算接口的状态枚举、幂等键及错误码。

评审后应分别形成《学习计划生成业务与接口契约》和《每日任务业务与接口契约》。本文中的阶段 3、4 在契约冻结前属于业务基线，不代表代码已经实现或验收通过。

## 10. 总体验收出口

四阶段整体完成必须由真实环境证据证明：一个新用户能够设置目标、完成诊断、获得真实初始画像、确认学习计划、完成当天任务，并看到计划进度和画像基于本次完成结果发生符合规则的变化；中途退出、重复操作、处理失败、跨设备恢复和目标暂停均有唯一且安全的结果。

只有主路径、异常路径、幂等性、数据一致性和真实数据展示全部通过，才能称为“首次学习闭环完成”。页面存在、接口返回成功、Mock 演示或单模块测试通过均不能单独作为完成结论。
