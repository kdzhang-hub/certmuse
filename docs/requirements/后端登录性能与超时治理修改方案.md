# CertMuse 后端登录性能与超时治理修改方案 V1

> 文档状态：待实施
> 适用范围：`backend/` 登录认证、登录态组装、入口类型解析、登录审计、数据库连接池
> 技术基线：Java 21、Spring Boot 4.1、Sa-Token、MyBatis-Plus、PostgreSQL 16、Redis/Redisson
> 本次范围：只治理后端登录慢、登录超时和登录成功后的同步阻塞；不修改验证码、Nginx、前端路由和用户角色写入逻辑

## 1. 结论

当前登录慢的主要风险不是“Java 线程不够”，而是一次登录为了组装登录态并行发起多条数据库查询，随后又重复查询角色和菜单权限。生产 Hikari 最大连接数只有 20，因此并行虚拟线程并不会增加数据库实际吞吐，只会让同一个登录请求更快地争抢多条连接。在并发登录时，少数请求可能占用大部分连接，其他请求最多等待 30 秒。

本方案采用以下顺序治理：

1. 先消除同一次登录中的重复角色、权限查询。
2. 登录态组装改为顺序查询并复用结果，使一个登录请求同一时刻最多占用一条数据库连接。
3. 保留`/system/user/getInfo`的入口复核，避免角色变更后旧会话继续使用。
4. 将在线列表写入、最近登录时间更新移出登录响应关键路径。
5. 异步事件只携带不可变快照，不再携带`HttpServletRequest`。
6. Hikari先保持20，完成压测后按20→24→32逐级评估；不直接大幅扩容。
7. 将数据库连接等待从30秒调整为5秒，使资源耗尽时快速失败并留下可识别指标。

不建议做以下操作：

- 不提高`ThreadUtils.virtualInvokeAll()`的线程数。它使用`newVirtualThreadPerTaskExecutor()`，本身没有固定线程数可以调大。
- 不先提高Jetty的`server.jetty.threads.max=256`。当前数据库连接池只有20，允许更多请求进入只会增加排队和内存压力。
- 不在本次开启全局`spring.threads.virtual.enabled=true`。Spring Boot 4.1开启虚拟线程后，自动配置的异步执行器会改变为虚拟线程执行器，并忽略普通线程池的池大小配置，不利于为登录后置任务建立明确的并发上限。
- 不通过无限队列或`CallerRunsPolicy`处理登录后置任务。无限队列会积压内存，`CallerRunsPolicy`会重新阻塞登录请求线程。

## 2. 当前实现

### 2.1 密码登录关键路径

当前`PasswordAuthStrategy.login()`执行顺序为：

```text
验证码Redis读取和删除
→ 用户查询
→ 密码校验与Redis失败次数处理
→ buildLoginUser()
→ AuthEntryResolver.resolve(userId)
→ Sa-Token创建Token及Session
→ markFirstLogin()条件更新sys_user
→ 返回登录结果
```

`buildLoginUser()`内部先查询部门，再通过`ThreadUtils.virtualInvokeAll()`并发执行四组任务：

```text
任务1：查询菜单权限
任务2：查询角色权限
      └─ 非超级管理员再次查询用户角色
任务3：查询用户角色
      └─ 根据角色查询数据权限映射
任务4：查询岗位
```

`buildLoginUser()`完成后，`PasswordAuthStrategy`再次调用`AuthEntryResolver.resolve(userId)`：

```text
再次查询用户角色
再次查询菜单权限
→ 计算entryType
```

登录成功后前端还会调用`GET /system/user/getInfo`。该接口为防止角色变更后旧会话继续使用，会再次查询角色和菜单权限并复核`entryType`，随后查询当前用户。

### 2.2 当前查询数量和连接占用

普通非超级管理员的一次密码登录，在进入`getInfo`前通常包含以下数据库操作：

| 顺序 | 当前操作 | 是否可能重复 |
| --- | --- | --- |
| 1 | 按用户名查询用户 | 否 |
| 2 | 查询部门 | 否 |
| 3 | 查询菜单权限 | 是 |
| 4 | 查询角色权限，内部查询角色 | 是 |
| 5 | 查询完整角色列表 | 是 |
| 6 | 按角色查询数据权限映射 | 否 |
| 7 | 查询岗位 | 否 |
| 8 | `AuthEntryResolver`再次查询角色 | 是 |
| 9 | `AuthEntryResolver`再次查询菜单权限 | 是 |
| 10 | 首次登录条件更新 | 已登录用户也执行一次UPDATE |

随后`getInfo`还会增加：

| 顺序 | 当前操作 |
| --- | --- |
| 11 | 再次查询角色 |
| 12 | 再次查询菜单权限 |
| 13 | 查询当前用户 |

实际SQL数量会因超级管理员分支和Mapper实现不同而变化，但以下事实固定成立：

- `buildLoginUser()`已取得角色和菜单权限后，密码登录又重复取得一次。
- `getRolePermission(userId)`和完整角色列表使用同一角色查询来源，可以复用完整角色列表计算角色权限码。
- 当前四个虚拟任务可能在同一时刻占用四条Hikari连接。
- Hikari最大连接数为20，单个登录请求在峰值时可能占用池容量的20%。

### 2.3 当前线程与连接池

| 类型 | 当前配置或实现 | 说明 |
| --- | --- | --- |
| Jetty请求线程 | `min=8`、`max=256` | 负责接收HTTP请求，不等于数据库连接数 |
| 登录查询虚拟线程 | 每次调用新建`newVirtualThreadPerTaskExecutor()` | 每个子任务一个虚拟线程，没有固定最大线程数 |
| Spring `@Async` | Spring Boot自动配置 | 当前未配置明确的队列容量和最大线程数 |
| Hikari | `maxPoolSize=20`、`minIdle=10` | 数据库并发硬上限 |
| Hikari等待 | `connectionTimeout=30000` | 连接耗尽时单个请求可等待30秒 |
| Redisson | `connectionPoolSize=64`、命令超时3秒 | Redis连接池与Hikari是两套独立资源 |

增加Java线程不能突破Hikari的20条连接上限。线程越多，只会有更多任务等待数据库连接。

### 2.4 当前登录成功后处理

Sa-Token创建Token时会同步触发`UserActionListener.doLogin()`，它同步发布`UserLoginSuccessEvent`。`UserLoginSuccessListener`当前没有`@Async`，因此以下操作仍处在登录响应关键路径：

1. 解析请求IP和User-Agent。
2. IP归属地查询。
3. 在线用户信息写入Redis。
4. 发布登录审计事件。
5. 更新`sys_user.login_ip`和`sys_user.login_date`。

`AddressUtils`使用本地`Ip2Region`数据，不是外部网络调用，但登录链路目前会在`LoginHelper.fillRequestContext()`和成功监听器中重复计算登录地址。

登录审计的数据库插入已经通过`@Async`执行，但`LoginInfoEvent`仍保存`HttpServletRequest`。异步线程在请求完成后访问Servlet请求对象存在生命周期风险，也使事件难以独立测试和重放。

## 3. 修改后的目标链路

```text
验证码和密码校验
→ 查询用户
→ 顺序构建登录上下文
   ├─ 查询部门
   ├─ 查询角色一次
   ├─ 查询菜单权限一次
   ├─ 使用已查角色计算角色权限码
   ├─ 使用已查角色和菜单权限计算entryType
   ├─ 查询数据权限映射
   └─ 查询岗位
→ 创建Sa-Token会话
→ 仅首次登录候选账号执行first_login_at条件更新
→ 将登录成功快照投递到有界后置执行器
→ 立即返回Token

后置执行器
├─ 写在线用户Redis
├─ 更新最近登录IP和时间
└─ 投递登录审计快照

GET /system/user/getInfo
→ 重新查询当前角色和菜单权限
→ 重新计算entryType并与Session比较
→ 查询当前用户
→ 返回身份信息
```

`getInfo`仍保留入口复核。这样会保留两次查询，但两次查询属于不同请求、承担不同职责：

- 登录请求内的计算用于创建可信会话。
- `getInfo`的重新计算用于发现登录后发生的角色和权限变化。

只有实现角色/权限版本号、角色变更后踢出会话或Token权限版本失效机制后，才能考虑删除`getInfo`的回查。

## 4. 具体代码修改

### 4.1 为入口解析增加“使用已加载数据”的重载

修改文件：

- `backend/ruoyi-modules/ruoyi-system/src/main/java/org/dromara/system/service/AuthEntryResolver.java`

保留现有`resolve(Long userId)`，供`getInfo`等需要读取数据库最新状态的调用方使用；新增一个不访问数据库的重载：

```java
public EntryType resolve(List<SysRoleVo> roles, Set<String> permissions) {
    List<SysRoleVo> enabledRoles = roles.stream()
        .filter(role -> SystemConstants.NORMAL.equals(role.getStatus()))
        .toList();
    return entryPolicy.resolve(enabledRoles, permissions);
}

public EntryType resolve(Long userId) {
    List<SysRoleVo> roles = roleService.selectRolesByUserId(userId);
    Set<String> permissions = permissionService.getMenuPermission(userId);
    return resolve(roles, permissions);
}
```

实现要求：

- 过滤启用角色的逻辑只保留一份，避免两个重载产生不同语义。
- `resolve(List, Set)`不得调用Mapper、Service或Redis。
- 角色为空、入口混合、权限缺失的行为继续由`AuthEntryPolicy`统一决定。

修改前：登录已查角色和权限，入口解析仍重新访问数据库。

修改后：登录直接使用本请求已查到的角色和权限；`getInfo`仍通过`resolve(userId)`读取最新状态。

### 4.2 支持使用已加载角色计算角色权限码

修改文件：

- `backend/ruoyi-modules/ruoyi-system/src/main/java/org/dromara/system/service/ISysPermissionService.java`
- `backend/ruoyi-modules/ruoyi-system/src/main/java/org/dromara/system/service/impl/SysPermissionServiceImpl.java`

新增重载：

```java
Set<String> getRolePermission(Long userId, List<SysRoleVo> roles);
```

实现逻辑：

```java
public Set<String> getRolePermission(Long userId, List<SysRoleVo> roles) {
    if (LoginHelper.isSuperAdmin(userId)) {
        return Set.of(SystemConstants.SUPER_ADMIN_ROLE_KEY);
    }
    Set<String> permissions = new HashSet<>();
    for (SysRoleVo role : roles) {
        if (ObjectUtil.isNotNull(role) && StringUtils.isNotBlank(role.getRoleKey())) {
            permissions.addAll(StringUtils.splitList(role.getRoleKey().trim()));
        }
    }
    return permissions;
}

public Set<String> getRolePermission(Long userId) {
    return getRolePermission(userId, roleService.selectRolesByUserId(userId));
}
```

实现要求：

- 必须保留超级管理员返回`superadmin`角色权限码的现有语义。
- 必须沿用现有`StringUtils.splitList()`规则，不能直接假设`roleKey`永远只有一个值。
- 旧方法继续保留，避免影响其他调用方。

修改前：`buildLoginUser()`分别查询角色权限和完整角色列表，底层重复查询角色。

修改后：完整角色列表只查一次，同时用于角色权限码、入口计算和数据权限映射。

### 4.3 重写`buildLoginUser()`为顺序查询和结果复用

修改文件：

- `backend/ruoyi-admin/src/main/java/org/dromara/web/service/SysLoginService.java`

删除该方法中的`ThreadUtils.virtualInvokeAll()`，按以下顺序组装登录上下文：

```java
public LoginUser buildLoginUser(SysUserVo user) {
    LoginUser loginUser = buildBasicLoginUser(user);
    Long userId = user.getUserId();

    fillDepartment(loginUser, user.getDeptId());

    List<SysRoleVo> roles = roleService.selectRolesByUserId(userId);
    Set<String> menuPermissions = permissionService.getMenuPermission(userId);
    Set<String> rolePermissions = permissionService.getRolePermission(userId, roles);
    EntryType entryType = authEntryResolver.resolve(roles, menuPermissions);

    List<RoleDTO> roleDtos = BeanUtil.copyToList(roles, RoleDTO.class);
    Map<String, List<Long>> dataScopeRoleMap = permissionService.getDataScopeRoleMap(roleDtos);
    List<SysPostVo> posts = postService.selectPostsByUserId(userId);

    loginUser.setMenuPermission(menuPermissions);
    loginUser.setRolePermission(rolePermissions);
    loginUser.setRoles(roleDtos);
    loginUser.setDataScopeRoleMap(dataScopeRoleMap);
    loginUser.setPosts(BeanUtil.copyToList(posts, PostDTO.class));
    loginUser.setEntryType(entryType.name());
    return loginUser;
}
```

这里故意使用顺序查询，而不是继续并行。原因如下：

- 当前最大数据库连接数只有20。
- 顺序查询使一个登录请求同一时刻只持有一条连接。
- 并发20个登录时，理论上最多20个查询占用连接，而不是5个登录就可能占满20条连接。
- 数据库本机或同机房单次索引查询通常只需毫秒级；减少排队后的P95/P99收益通常大于低并发下并行节省的少量时间。
- 顺序实现更容易记录每个阶段耗时和定位慢SQL。

如果压测证实数据库连接长期有充足余量，而单请求P50仍不达标，可以在第二阶段只并行两组互不依赖查询，例如“菜单权限”和“岗位”，但并发上限必须固定为2，不能重新使用每任务一个虚拟线程的无限并行模式。

修改前：一次登录并行抢占多条数据库连接，并重复查询角色和菜单。

修改后：一次登录同一时刻最多占一条数据库连接，角色和菜单只在该请求中查询一次。

### 4.4 删除密码策略中的第二次入口查询

修改文件：

- `backend/ruoyi-admin/src/main/java/org/dromara/web/service/impl/PasswordAuthStrategy.java`

删除：

```java
try {
    loginUser.setEntryType(authEntryResolver.resolve(user.getUserId()).name());
} catch (ServiceException e) {
    ...
}
```

`buildLoginUser()`返回时必须已经完成入口解析并设置`entryType`。入口配置无效时，`buildLoginUser()`直接失败，不创建Token。

需要同时统一异常映射：

- 新增面向登录的统一错误文案，例如`user.account.entry.invalid=账号暂时无法登录，请联系管理员`。
- 服务端日志记录`userId`、认证方式和内部原因码，但不向客户端返回角色名称、权限码或配置详情。
- 密码、短信、邮箱和第三方登录使用一致的入口失败行为。

`buildLoginUser()`同时被以下策略调用：

- `PasswordAuthStrategy`
- `EmailAuthStrategy`
- `SmsAuthStrategy`
- `SocialAuthStrategy`

因此把入口解析放入`buildLoginUser()`不仅是查询优化，也会保证不同认证方式使用同一套入口规则。实现时必须为这四种策略补充回归测试。

### 4.5 避免已登录用户每次执行首次登录UPDATE

修改文件：

- `backend/ruoyi-modules/ruoyi-system/src/main/java/org/dromara/system/domain/vo/SysUserVo.java`
- `backend/ruoyi-admin/src/main/java/org/dromara/web/service/impl/PasswordAuthStrategy.java`
- 视映射情况修改对应MapStruct或VO映射测试

在`SysUserVo`增加：

```java
private LocalDateTime firstLoginAt;
```

登录最初的用户查询会一并取得该字段。返回登录结果时：

```java
boolean firstLogin = false;
if (user.getFirstLoginAt() == null) {
    firstLogin = loginService.markFirstLogin(user.getUserId());
}
loginVo.setFirstLogin(firstLogin);
```

数据库条件更新仍保留：

```sql
UPDATE sys_user
SET first_login_at = CURRENT_TIMESTAMP
WHERE user_id = ?
  AND first_login_at IS NULL;
```

修改前：每次密码登录都发送一次UPDATE，已登录过的账号影响行数为0。

修改后：绝大多数老用户不再发送该UPDATE；首次并发登录仍由数据库条件更新保证只有一个请求返回`firstLogin=true`。

### 4.6 将登录成功后置工作移出响应关键路径

修改文件：

- `backend/ruoyi-admin/src/main/java/org/dromara/web/listener/UserActionListener.java`
- `backend/ruoyi-admin/src/main/java/org/dromara/web/event/UserLoginSuccessEvent.java`
- `backend/ruoyi-admin/src/main/java/org/dromara/web/listener/UserLoginSuccessListener.java`
- `backend/ruoyi-common/ruoyi-common-satoken/src/main/java/org/dromara/common/satoken/utils/LoginHelper.java`
- 新增`backend/ruoyi-admin/src/main/java/org/dromara/web/config/AuthAsyncConfig.java`
- 新增`backend/ruoyi-admin/src/main/java/org/dromara/web/service/AuthPostLoginDispatcher.java`

#### 4.6.1 事件改为不可变快照

当前事件保存`SaLoginParameter`，监听器再访问Servlet请求。改为只保存执行后置任务所需的字段：

```java
public record UserLoginSuccessEvent(
    Long userId,
    String username,
    String tokenValue,
    long tokenTimeout,
    String clientKey,
    String deviceType,
    String deptName,
    String ip,
    String loginLocation,
    String browser,
    String os,
    Instant occurredAt
) {
}
```

在`LoginHelper.fillRequestContext()`完成IP、归属地和UA计算后，把这些值作为登录参数extra传给Sa-Token监听器。`UserActionListener.doLogin()`只从参数extra中构造事件，不再访问或传递`HttpServletRequest`。

这样可以复用`LoginHelper`已经计算的地址信息，删除成功监听器中的第二次IP归属地计算。

#### 4.6.2 同步监听器只负责投递

`UserLoginSuccessListener`继续使用同步`@EventListener`，但方法内部不再直接访问Redis和数据库，只调用：

```java
authPostLoginDispatcher.trySubmit(event);
```

`trySubmit()`必须捕获`TaskRejectedException`和其他提交异常：

```java
public void trySubmit(UserLoginSuccessEvent event) {
    try {
        executor.execute(() -> process(event));
    } catch (TaskRejectedException e) {
        metrics.postLoginRejected();
        log.warn("post-login task rejected, userId={}", event.userId());
    }
}
```

不能只给监听器增加`@Async`，因为线程池拒绝任务时，提交异常仍可能沿事件发布链返回登录线程。显式dispatcher可以保证后置任务拒绝时不会把已创建的Token变成登录失败。

#### 4.6.3 后置任务内容

`process(event)`执行：

1. 构造`UserOnlineDTO`并写入Redis在线列表。
2. 更新`sys_user.login_ip`和`sys_user.login_date`。
3. 发布或投递登录审计快照。
4. 分步骤捕获异常，在线列表失败不能阻止最近登录时间和审计继续执行。

Token、Token Session和核心认证状态仍由`LoginHelper.login()`同步写Redis。只有监控在线列表属于非核心后置数据。

修改前：在线列表Redis失败或最近登录时间数据库失败可能使登录接口报错，Token却可能已经部分创建。

修改后：Token创建成功即可返回；后置记录失败只告警和计数，不撤销认证结果。

### 4.7 登录审计事件移除`HttpServletRequest`

修改文件：

- `backend/ruoyi-common/ruoyi-common-log/src/main/java/org/dromara/common/log/event/LoginInfoEvent.java`
- `backend/ruoyi-admin/src/main/java/org/dromara/web/service/SysLoginService.java`
- `backend/ruoyi-admin/src/main/java/org/dromara/web/service/SysRegisterService.java`
- `backend/ruoyi-modules/ruoyi-system/src/main/java/org/dromara/system/service/impl/SysLoginInfoServiceImpl.java`

`LoginInfoEvent`改为不可变字段或record：

```java
public record LoginInfoEvent(
    String username,
    String status,
    String message,
    String ip,
    String browser,
    String os,
    String clientId,
    Instant occurredAt,
    Object[] args
) {
}
```

请求线程发布事件前完成：

- IP提取；
- User-Agent解析；
- clientId提取；
- 时间戳生成。

异步消费者只处理普通数据，不读取`HttpServletRequest`。

如果成功登录事件已经携带相同快照，登录成功审计直接从`UserLoginSuccessEvent`转换，不能再次解析请求。

修改前：异步线程持有Servlet请求对象，生命周期和线程安全边界不明确。

修改后：事件可独立测试、可安全异步执行，也不会意外持有请求体、Cookie或其他敏感上下文。

### 4.8 新增专用有界执行器

修改文件：

- 新增`backend/ruoyi-admin/src/main/java/org/dromara/web/config/AuthAsyncConfig.java`
- `backend/ruoyi-admin/src/main/resources/application.yml`
- `backend/ruoyi-admin/src/main/resources/application-prod.yml`

建议配置两个执行器，隔离登录后置状态和审计日志：

| 执行器 | core | max | queue | 用途 |
| --- | ---: | ---: | ---: | --- |
| `loginPostProcessorExecutor` | 2 | 4 | 200 | 在线列表、最近登录时间 |
| `authAuditExecutor` | 1 | 2 | 500 | 登录、退出、注册和认证失败审计 |

建议使用`ThreadPoolTaskExecutor`：

```java
@Bean("loginPostProcessorExecutor")
public ThreadPoolTaskExecutor loginPostProcessorExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(2);
    executor.setMaxPoolSize(4);
    executor.setQueueCapacity(200);
    executor.setKeepAliveSeconds(60);
    executor.setThreadNamePrefix("auth-post-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
    executor.setWaitForTasksToCompleteOnShutdown(true);
    executor.setAwaitTerminationSeconds(10);
    executor.initialize();
    return executor;
}
```

参数必须支持环境变量覆盖，例如：

```yaml
certmuse:
  auth:
    async:
      post-login:
        core-size: ${CERTMUSE_AUTH_POST_CORE_SIZE:2}
        max-size: ${CERTMUSE_AUTH_POST_MAX_SIZE:4}
        queue-capacity: ${CERTMUSE_AUTH_POST_QUEUE_CAPACITY:200}
      audit:
        core-size: ${CERTMUSE_AUTH_AUDIT_CORE_SIZE:1}
        max-size: ${CERTMUSE_AUTH_AUDIT_MAX_SIZE:2}
        queue-capacity: ${CERTMUSE_AUTH_AUDIT_QUEUE_CAPACITY:500}
```

执行器不能放进现有`scheduledExecutorService`。该线程池只负责周期任务，并使用`CallerRunsPolicy`，不适合登录后置工作。

初始值不应开得更高，原因是后置任务最终仍会访问同一个Redis和Hikari。`post-login max=4`表示最多额外占用4条数据库连接，给前台业务和登录主链路保留资源。

## 5. Hikari和线程参数调整

### 5.1 第一阶段推荐配置

修改文件：

- `backend/ruoyi-admin/src/main/resources/application-prod.yml`

第一阶段在完成查询去重后使用：

```yaml
hikari:
  maxPoolSize: 20
  minIdle: 10
  connectionTimeout: 5000
  validationTimeout: 2000
  idleTimeout: 600000
  maxLifetime: 1800000
  keepaliveTime: 30000
```

变化：

- `maxPoolSize`先保持20，避免代码和容量同时变化导致无法判断收益来源。
- `connectionTimeout`由30秒降为5秒。数据库连接耗尽时快速返回受控错误，不让用户一直等待。
- `validationTimeout`由5秒降为2秒，连接校验异常更快暴露。

快速失败必须配合统一异常处理，把连接获取超时转换为真实HTTP 503和固定错误码；不能继续返回模糊500。

### 5.2 什么时候可以提高到24或32

完成查询去重和压测后，同时满足以下条件才增加连接数：

1. Hikari `active`持续接近20，`pending`大于0。
2. PostgreSQL CPU峰值低于60%～70%。
3. PostgreSQL不存在明显锁等待和慢SQL。
4. 数据库`max_connections`扣除管理员连接、维护连接和其他应用后仍有余量。
5. 当前应用实例数量已纳入总连接预算。

连接预算必须满足：

```text
单实例maxPoolSize × 应用实例数
+ 迁移/维护预留
+ 管理员预留
+ 其他服务连接
< PostgreSQL max_connections
```

调整步骤：

```text
20 → 压测 → 24 → 压测 → 32
```

每次只增加一个档位。如果24与32相比吞吐没有明显增长，或者数据库CPU、锁等待、查询P95明显上升，应回退到24或20。

不建议未经生产规格和压测直接设置50、64或100。连接数越高并不代表吞吐越高，PostgreSQL会为更多活跃连接承担内存、上下文切换和锁竞争成本。

### 5.3 其他线程配置是否调整

| 配置 | 是否调整 | 原因 |
| --- | --- | --- |
| `server.jetty.threads.max=256` | 暂不调整 | 当前不是已确认瓶颈；提高会放大数据库排队 |
| `spring.threads.virtual.enabled=false` | 保持 | 避免改变全局异步执行语义；登录查询不再需要虚拟并发 |
| `ThreadUtils` | 不修改公共工具 | 其他模块仍可能需要虚拟线程；只从登录路径移除调用 |
| Redisson `connectionPoolSize=64` | 暂不提高 | 已高于Hikari，需先观察Redis timeout和连接使用率 |
| 登录后置执行器 | 新增2/4和1/2两个小池 | 隔离非关键任务并限制其对数据库的冲击 |

## 6. 可观测性

仅修改代码而不增加指标，无法判断调优是否有效。至少增加以下Micrometer指标：

| 指标 | 类型 | 标签限制 | 用途 |
| --- | --- | --- | --- |
| `certmuse.auth.login.duration` | Timer | `strategy`、`result` | 登录总耗时 |
| `certmuse.auth.login.stage.duration` | Timer | 固定`stage`枚举 | 用户、角色、菜单、岗位、Token等阶段耗时 |
| `certmuse.auth.post_login.rejected` | Counter | 无用户标签 | 后置执行器拒绝数 |
| `certmuse.auth.post_login.failed` | Counter | 固定步骤枚举 | Redis、最近登录时间、审计失败数 |
| `certmuse.auth.entry.invalid` | Counter | `strategy` | 入口配置失败数 |

禁止把用户名、userId、Token、IP作为指标标签，避免高基数和隐私泄露。具体用户只写脱敏日志。

Hikari已有Micrometer集成能力，需要采集：

- `hikaricp.connections.active`
- `hikaricp.connections.idle`
- `hikaricp.connections.pending`
- `hikaricp.connections.timeout`
- 数据库查询P95/P99

生产当前只对外暴露`health,info`。不要为了看指标直接把`/actuator/metrics`公开到公网；应通过受控运维通道、内部监控或日志汇总读取。

登录阶段日志建议采用固定字段：

```text
requestId
strategy
result
totalMs
userQueryMs
roleQueryMs
menuPermissionMs
dataScopeMs
postQueryMs
tokenMs
```

慢登录阈值初始设为2秒。超过阈值记录WARN，但不得记录密码、验证码、Token、Cookie和权限全集。

## 8. 修改前后区别

| 维度 | 当前实现 | 修改后 |
| --- | --- | --- |
| 登录角色查询 | 多次查询 | 登录请求内一次查询并复用 |
| 登录菜单权限查询 | `buildLoginUser`一次，入口解析再一次 | 登录请求内一次查询并复用 |
| 角色权限计算 | 再查一次角色 | 使用完整角色列表内存计算 |
| 登录查询并发 | 一个请求最多并行4组数据库任务 | 一个请求同一时刻最多1条数据库查询 |
| Hikari占用公平性 | 少量登录可同时占用大部分连接 | 更多登录请求可公平轮转使用连接 |
| 连接耗尽等待 | 最多30秒 | 最多5秒并返回受控503 |
| entryType计算 | 密码登录单独再次解析 | 所有调用`buildLoginUser`的认证策略统一解析 |
| `getInfo`入口复核 | 读取最新角色权限 | 保持不变，继续保障会话安全 |
| 最近登录时间 | 阻塞登录响应 | 后置执行，失败不撤销Token |
| 在线用户缓存 | 阻塞登录响应 | 后置执行，失败只告警 |
| IP归属地 | 登录上下文和成功监听器重复计算 | 计算一次并通过快照复用 |
| 登录审计事件 | 异步线程读取`HttpServletRequest` | 只读取不可变普通字段 |
| 异步资源 | 使用全局默认执行器，边界不清 | 登录后置和审计使用专用有界执行器 |
| 扩容方式 | 可能直接提高线程或连接数 | 先减查询，再按指标20→24→32调优 |

### 9.2 集成测试

使用PostgreSQL和Redis测试环境验证：

- 密码、短信、邮箱、第三方登录均能得到正确`entryType`。
- 登录后立刻调用`getInfo`，返回入口与Session一致。
- 角色在登录后改变时，`getInfo`能注销失效会话。
- 在线列表Redis不可用时，核心Token创建策略按设计执行。
- 后置执行器队列满时，登录接口仍能返回，不发生请求线程执行后置任务。
- 数据库连接获取超时返回真实HTTP 503和固定错误结构。

### 9.3 压测

压测必须分三组，使用同一组账号分布、数据库数据量和机器规格：

| 场景 | 并发 | 持续时间 | 目的 |
| --- | ---: | ---: | --- |
| 基线 | 1 | 3分钟 | 比较P50单请求耗时 |
| 常规峰值 | 20 | 10分钟 | 对齐当前Hikari容量 |
| 压力场景 | 50 | 10分钟 | 验证排队、快速失败和恢复能力 |

采集：

- 登录成功率；
- P50、P95、P99；
- Hikari active、idle、pending、timeout；
- PostgreSQL CPU、活动连接、锁等待、慢SQL；
- Redis命令P95和timeout；
- 后置执行器active、queue size、rejected；
- JVM CPU、堆、GC停顿。

建议验收目标：

- 正常依赖下，单并发登录P95小于1秒。
- 20并发登录P95小于2秒，P99小于3秒。
- Hikari pending不持续增长。
- 正常压测中后置执行器拒绝数为0。
- 依赖故障时5秒内返回受控503，不出现30秒等待。
- 不产生新的502；如果Java进程退出，仍需通过Nginx和systemd日志另行定位。

目标值需根据生产服务器CPU、内存和数据库规格在首次压测后校准，不能把未测量的数据写成已达成结果。

## 10. 实施顺序

### 第一批：查询去重

1. 增加`AuthEntryResolver.resolve(List, Set)`。
2. 增加使用已有角色计算角色权限的重载。
3. 重写`buildLoginUser()`。
4. 删除密码策略中的第二次入口查询。
5. 增加四类认证策略回归测试。

这一批可独立上线，风险较低，能够直接减少SQL和连接争抢。

### 第二批：后置任务隔离

1. 设计不可变登录成功快照。
2. 增加专用有界执行器和dispatcher。
3. 移出在线状态和最近登录时间更新。
4. 登录审计事件移除`HttpServletRequest`。
5. 增加拒绝、Redis失败和数据库失败测试。

这一批改变登录成功后的时序，需要重点验证在线用户页面和最近登录时间的最终一致性。

### 第三批：配置与容量

1. 将Hikari连接等待改为5秒。
2. 增加指标和阶段耗时日志。

## 11. 回滚方案

- 查询去重回滚：恢复旧`buildLoginUser()`和密码策略入口解析；新增重载可暂时保留，不影响行为。
- 后置任务回滚：恢复同步监听器。事件快照字段可以保留，无需重新引入`HttpServletRequest`。
- Hikari回滚：将`maxPoolSize`恢复20、`connectionTimeout`恢复原值。建议只回滚容量，不回滚指标。
- 不涉及数据库结构变更；`SysUserVo.firstLoginAt`只是读取已有字段，不需要数据库回滚。

## 12. 完成标准

只有同时满足以下条件才算完成：

- 登录请求内角色和菜单权限各只查询一次。
- 登录路径不再调用`ThreadUtils.virtualInvokeAll()`。
- 所有认证策略通过同一个`buildLoginUser()`计算入口类型。
- `getInfo`仍能发现角色/权限变化并注销不一致会话。
- 登录成功后置任务失败不会使已创建的Token请求失败。
- 所有异步登录事件不再携带`HttpServletRequest`、密码、验证码、Cookie和完整Token。
- 异步执行器队列有界，拒绝策略不是`CallerRunsPolicy`。
- Hikari调整经过20、24、32分档压测，而不是直接猜测。
- 单元测试、集成测试、后端完整测试和打包通过。
- 部署通过RouteFlow Deployer执行，正式发布前先完成dry-run。
