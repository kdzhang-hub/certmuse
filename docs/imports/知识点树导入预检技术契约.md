## 1. 文档职责

本文统一规定：

1. `subject_no -> cm_exam_subject.id` 显式映射；
2. `cm_import_batch`、`cm_import_record`、`cm_import_issue` 与 `cm_knowledge_point` 的责任边界；
3. 四个预检接口的请求、响应、状态、错误码、分页和统计口径；
4. 非法 JSON 的兼容处理和后续设计债务；
5. 幂等、安全、异常处理和正式知识点零写入的复核要求。

[知识点树 JSONL 导入规范 V1](知识点树JSONL导入规范.md)继续作为13个 JSONL 字段、类型、枚举和 `KP_*` 行级问题码的唯一来源。本文不复制或改变该规范。

## 2. 预检范围

### 2.1 包含

```text
选择考纲版本和科目映射
-> 上传 knowledge_point JSONL
-> 创建唯一导入批次
-> 触发文件和数据预检
-> 查询进度与统计
-> 分页查询问题
```

### 2.2 不包含

- 确认导入和正式知识点写入；
- 失败记录重试；
- 租约、心跳、重启恢复和自动重试；
- 题目、教材和其他导入类型；
- 生产级大文件性能承诺。

`waiting_confirm`只表示“预检完成”，页面不得展示确认按钮或“导入成功”。

## 3. 当前项目事实和开发前置

### 3.1 可直接复用的 RuoYi 能力

| 能力 | 当前项目实际格式 | 预检使用方式 |
| --- | --- | --- |
| 统一响应 | `R<T>`，顶层为 `code/msg/data` | 四接口全部复用 |
| 分页响应 | `PageResult<T>`，只有 `rows/total` | 问题列表复用 |
| 分页请求 | `PageQuery` | 使用 `pageNum/pageSize/orderByColumn/isAsc` |
| 文件上传 | `MultipartFile` 和 `multipart/form-data` | JSONL 上传复用 |
| 权限 | Sa-Token `@SaCheckPermission` | 四接口统一鉴权 |
| 日志 | RuoYi `@Log` 和全局日志体系 | 记录管理操作，过滤文件正文 |
| 对象存储 | `ruoyi-common-oss`、MinIO 私有桶 | 使用底层 `OssClient` |
| 异步 | Spring `TaskExecutor`、`@Async` | 独立 Worker 执行；预检任务持久化到 `cm_async_job` |

### 3.2 不能直接复用或不能声称已具备

- 当前 `R<T>` 没有顶层 `traceId` 和稳定业务错误码字段；
- 当前 `PageResult<T>` 不返回 `pageNum/pageSize`；
- `@RepeatSubmit` 只能防止短时间重复提交，不能替代业务幂等；
- `SysOssService.upload` 会写入 `sys_oss` 并返回临时 URL，不符合导入批次只保存对象键和哈希的边界；
- Jackson 当前配置会忽略未知字段，不能依赖 DTO 反序列化完成13字段白名单校验；
- Spring 进程内异步不能单独承担任务恢复；当前预检通过 `cm_async_job` 持久化任务和租约字段补足该边界；
- 导入能力位于 `backend/ruoyi-modules/ruoyi-certmuse` 的 `catalog` 包。预检使用的 PostgreSQL 16 脚本、JSONB 配置、约束、索引和验收断言已同步并完成验证。

### 3.3 已完成的实现基线

1. 后端已在 `ruoyi-certmuse` 模块接入知识点树预检能力；
2. `backend/script/sql/postgres/certmuse/`的 PostgreSQL 16 脚本及 `verify_local.sql` 已同步预检约束、JSONB 配置变体和验收断言；
3. 后端和测试已使用 PostgreSQL 16 验证 JSONB、外键和 `NULLS NOT DISTINCT` 约束；
4. 当前使用 MySQL 的本地 Docker 编排不作为本功能的数据库验收环境；
5. 文件上限沿用当前全局限制：单文件不超过10MB，不修改全局上传配置。

本功能数据库基线固定为PostgreSQL 16。迁移、JSONB映射、约束、索引和验收均只按PostgreSQL 16执行，不设计MySQL兼容分支，也不以当前MySQL本地编排结果代替预检数据库验收。

上述基线已完成。后续变更不得以 MySQL 本地编排结果替代 PostgreSQL 16 验收。

## 5. `subject_no` 显式映射

### 5.1 请求结构

`subjectMappings` 是 `multipart/form-data` 中的 JSON 字符串。反序列化后的结构固定为：

```json
[
  {"subjectNo": 1, "examSubjectId": "101"},
  {"subjectNo": 2, "examSubjectId": "102"},
  {"subjectNo": 3, "examSubjectId": "103"}
]
```

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `subjectNo` | integer | 来源文件中的科目编号，只允许1、2、3，不是数据库ID |
| `examSubjectId` | string(int64) | 目标 `cm_exam_subject.id`的十进制字符串，服务端校验后转换为Java `Long` |

### 5.2 校验顺序

1. `subjectMappings` 必填，数组长度为1至3；
2. `subjectNo` 只能为整数1、2、3，同一批次内不得重复；
3. `examSubjectId` 必须匹配`^[1-9][0-9]{0,18}$`且转换后不超过Java `Long`上限，同一批次内不得重复；
4. `cm_exam_subject.id` 必须存在；
5. `cm_exam_subject.certification_id` 必须等于所选 `cm_syllabus_version.certification_id`；
6. 映射按 `subjectNo` 升序规范化；
7. 规范化结果冻结到 `cm_import_batch.parse_config.subject_mappings`；
8. JSONL 实际出现的每个 `subject_no` 必须能够精确命中映射。

冻结后的 `parse_config`：

```json
{
  "schema_version": "import_parse_config/1.0",
  "subject_mappings": [
    {"subject_no": 1, "exam_subject_id": 101},
    {"subject_no": 2, "exam_subject_id": 102},
    {"subject_no": 3, "exam_subject_id": 103}
  ]
}
```

### 5.3 失败处理

- 请求中的映射格式错误、重复、不存在或跨考试资格：返回 `IMPORT_CONTEXT_INVALID`，不创建批次；
- JSONL 行使用未配置的 `subject_no`：创建 `KP_SUBJECT_MAPPING_UNKNOWN` 行级 error；
- 额外但合法的映射可以保留，但不得据此生成知识点或科目；
- 禁止按科目名称、知识点标题、编号前缀或已有数据数量猜测；
- 禁止自动创建、自动启用、自动修改 `cm_exam_subject`。

## 6. 四张表的责任边界

本节“四张表”固定指`cm_import_batch`、`cm_import_record`、`cm_import_issue`和后续目标表`cm_knowledge_point`。`cm_idempotency_record`和`cm_async_job`是通用支撑表，不计入“四张表”。

### 6.1 `cm_import_batch`

负责保存一次导入的上下文和执行快照：

- `request_id`；
- `syllabus_version_id`；
- MinIO 私有对象键和服务端 SHA-256；
- `import_type/template_version/parser_version/parse_config`；
- 状态、当前阶段、进度和统计；
- 批次级故障摘要和 `trace_id`。

知识点树可包含多个考试科目，因此：

```text
cm_import_batch.exam_subject_id = NULL
cm_import_batch.generated_count = 0
cm_import_batch.confirmed_by = NULL
cm_import_batch.confirmed_time = NULL
```

文件哈希、模板、考纲版本和科目映射在批次创建后冻结，预检接口不得接收新值覆盖。

时间字段语义固定如下：

- `create_time`表示批次创建时间；
- `started_time`在批次创建时为`NULL`，`uploaded -> parsing`成功后由服务端写入且此后不得覆盖；
- `finished_time`只在进入`waiting_confirm`或`failed`时写入；
- API中的`createTime/startedTime/finishedTime`分别对应上述三个字段。

### 6.2 `cm_import_record`

- 只有整行能够解析为 JSON 对象时才创建；
- `source_line_no` 保存原始行号；
- `source_key` 从合法对象提取；
- `raw_record` 保存合法 JSONB，`raw_hash` 保存该行 SHA-256；
- 初始状态为 `pending`；无 error 后为 `success`，存在 error 后为 `failed`；
- 预检不使用 `skipped`，`result_data=NULL`；
- 同一批次内 `source_line_no` 唯一。

### 6.3 `cm_import_issue`

- 保存 warning/error、稳定问题码、字段路径和脱敏中文说明；
- 合法 JSON 问题关联 `import_record_id`；
- 非法 JSON 问题的 `import_record_id=NULL`；
- 预检新问题状态统一为 `open`；
- 不保存完整非法行、对象键、凭据和内部异常堆栈。

### 6.4 `cm_knowledge_point`

预检仅把该表视为后续目标表。上传和预检不得：

- 新增知识点；
- 修改名称、层级、开关、状态或排序；
- 删除或逻辑删除知识点；
- 根据问题结果自动补齐父节点或科目。

验收必须证明预检前后正式知识点数量、内容摘要和更新时间不变。

## 7. RuoYi 统一接口格式

### 7.1 成功响应

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {}
}
```

### 7.2 错误响应

不修改公共 `R<T>`。导入模块需要的稳定错误信息放入 `data`：

```json
{
  "code": 409,
  "msg": "请求号已被不同载荷使用",
  "data": {
    "errorCode": "IMPORT_REQUEST_ID_CONFLICT",
    "retryable": false,
    "traceId": null,
    "fieldErrors": []
  }
}
```

`ImportErrorVo`固定包含以下字段：

| 字段 | JSON类型 | 必返 | 可空 | 说明 |
| --- | --- | --- | --- | --- |
| `errorCode` | string | 是 | 否 | 第14节稳定业务错误码 |
| `retryable` | boolean | 是 | 否 | 当前请求是否允许在条件不变时重试 |
| `traceId` | string | 是 | 是 | 系统故障定位号；没有可公开定位号时为`null` |
| `fieldErrors` | array | 是 | 否 | 字段错误列表；没有字段错误时返回空数组 |

`fieldErrors[]`固定为：

| 字段 | JSON类型 | 必返 | 可空 | 说明 |
| --- | --- | --- | --- | --- |
| `field` | string | 是 | 否 | 请求字段路径，例如`subjectMappings[0].examSubjectId` |
| `code` | string | 是 | 否 | 稳定字段错误码，例如`SUBJECT_NOT_FOUND` |
| `message` | string | 是 | 否 | 可展示的脱敏中文说明 |

字段路径使用请求中的camelCase名称。不得在`message`中返回SQL、对象键、文件正文、内部类名或异常堆栈。

`fieldErrors[].code`只允许：`REQUIRED`、`INVALID_FORMAT`、`OUT_OF_RANGE`、`DUPLICATE`、`NOT_FOUND`、`CERTIFICATION_MISMATCH`和`UNSUPPORTED`。新增字段错误码必须按第20节升级契约，不能临时返回异常类名或数据库约束名。

当前公共`R<T>`没有`fail(code, msg, data)`工厂方法。预检不修改公共`R<T>`，由导入模块提供唯一的`ImportResponses.fail(int code, String msg, ImportErrorVo data)`构造入口；Controller和异常转换器不得各自手工拼装错误响应。

本文的400、403、404、409和500默认指响应体中的 `R.code`。当前 RuoYi 部分异常不会同步设置真实 HTTP Status，前端必须读取 `R.code`，不能只依赖 HTTP Status。

### 7.3 权限

四接口统一使用权限标识：

```text
certmuse:catalog:import
```

查询批次前必须检查权限和数据范围。无权访问时不得返回文件名、批次状态、创建人、对象键和哈希。

三个批次子资源接口中的`{id}`固定为十进制正整数文本，服务端校验后转换为Java `Long`。格式错误返回`IMPORT_CONTEXT_INVALID`并使用`fieldErrors.field=id`；格式正确但批次不存在或不可见时统一返回`IMPORT_BATCH_NOT_FOUND`。

## 8. 接口一：创建批次

```http
POST /api/admin/imports
Content-Type: multipart/form-data
X-Request-Id: 0f7cd9a8-4b29-4ba5-b202-b7fb5aac85dd
```

| 字段 | 位置 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- | --- |
| `X-Request-Id` | header | string | 是 | 1至100字符，全局唯一，推荐UUID |
| `file` | part | binary | 是 | UTF-8 JSONL，不超过10MiB |
| `importType` | param | string | 是 | 固定 `knowledge_point` |
| `syllabusVersionId` | param | string(int64) | 是 | 十进制正整数，必须存在；服务端校验后转换为Java `Long` |
| `templateVersion` | param | string | 是 | 固定 `knowledge_point/1.0` |
| `subjectMappings` | param | JSON string | 是 | 使用第5节结构 |

### 8.1 文件接收边界

- 文件名扩展名只允许`.jsonl`，大小写不敏感；
- 文件必须非空，服务端接收上限为10MiB，即10,485,760字节；
- 允许的`Content-Type`为`application/x-ndjson`、`application/jsonl`、`application/json`、`text/plain`和`application/octet-stream`；浏览器未提供类型时允许为空，但不能只依赖MIME判断文件是否合法；
- 编码必须是严格UTF-8，不允许UTF-8 BOM，不允许使用替换字符吞掉非法字节；
- 支持LF和CRLF，文件末尾换行可有可无；行终止符本身不生成额外空行；
- 只包含空白字符的物理行按非法JSON处理并计入行号；
- 每个物理行去除行终止符后的UTF-8字节数不得超过1MiB，即1,048,576字节；`LF`、`CRLF`和文件末尾不存在的行终止符均不计入。UTF-8 BOM按文件级错误处理，超限行不进入JSON解析，生成`KP_JSON_LINE_TOO_LARGE`；
- 每行根节点必须是JSON对象。数组、字符串、数字、布尔值和`null`统一生成`KP_JSON_INVALID`；
- 文件为空、扩展名不符、整体超限、BOM或UTF-8非法时返回`IMPORT_FILE_INVALID`且不创建批次；行级错误不阻止创建批次。

返回类型：`R<ImportBatchVo>`。

`ImportBatchVo`字段固定为：

| 字段 | JSON类型 | 必返 | 可空 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | string(int64) | 是 | 否 | 导入批次ID的十进制字符串 |
| `importType` | string | 是 | 否 | 固定`knowledge_point` |
| `syllabusVersionId` | string(int64) | 是 | 否 | 考纲版本ID的十进制字符串 |
| `templateVersion` | string | 是 | 否 | 固定`knowledge_point/1.0` |
| `status` | string | 是 | 否 | 创建成功固定为`uploaded` |
| `reused` | boolean | 是 | 否 | 是否命中同请求号、同载荷的既有批次 |
| `createTime` | string(date-time) | 是 | 否 | ISO 8601，带时区偏移 |

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "id": "10001",
    "importType": "knowledge_point",
    "syllabusVersionId": "20001",
    "templateVersion": "knowledge_point/1.0",
    "status": "uploaded",
    "reused": false,
    "createTime": "2026-07-30T10:30:00+08:00"
  }
}
```

响应不返回对象键、文件哈希、解析配置和临时下载 URL。

本接口可能返回：`IMPORT_FILE_INVALID`、`IMPORT_CONTEXT_INVALID`、`IMPORT_FORBIDDEN`、`IMPORT_REQUEST_ID_CONFLICT`、`IMPORT_SYSTEM_FAILURE`。

## 9. 接口二：触发预检

```http
POST /api/admin/imports/10001/validate
```

无请求体，不要求新的 `X-Request-Id`。返回类型：`R<ImportValidationAcceptedVo>`。

`ImportValidationAcceptedVo`字段固定为：

| 字段 | JSON类型 | 必返 | 可空 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | string(int64) | 是 | 否 | 导入批次ID的十进制字符串 |
| `status` | string | 是 | 否 | 当前批次状态 |
| `currentStage` | string | 是 | 是 | 当前处理阶段；尚未形成阶段时为`null` |
| `accepted` | boolean | 是 | 否 | 本次调用是否首次成功提交预检任务 |

| 当前状态 | 处理 | `accepted` |
| --- | --- | --- |
| `uploaded` | 在一个事务中条件更新为 `parsing`，并写入一条`knowledge_point_precheck`待执行任务 | true |
| `parsing`、`validating` | 返回当前任务，不重复提交 | false |
| `waiting_confirm` | 返回已有结果 | false |
| `failed` | 返回 `IMPORT_BATCH_STATE_INVALID` | 不返回成功结果 |

```json
{
  "code": 200,
  "msg": "预检任务已受理",
  "data": {
    "id": "10001",
    "status": "parsing",
    "currentStage": "read_jsonl",
    "accepted": true
  }
}
```

状态更新和`knowledge_point_precheck`任务写入必须处于同一数据库事务，不能只使用 JVM 内存锁或“更新状态后直接提交线程”的方式。事务失败时批次保持`uploaded`，接口返回`IMPORT_SYSTEM_FAILURE`；事务提交后由任务分发器领取任务。

本接口可能返回：`IMPORT_FORBIDDEN`、`IMPORT_BATCH_NOT_FOUND`、`IMPORT_BATCH_STATE_INVALID`、`IMPORT_SYSTEM_FAILURE`。

## 10. 接口三：查询进度

```http
GET /api/admin/imports/10001/progress
```

返回类型：`R<ImportProgressVo>`。

`ImportProgressVo`字段固定为：

| 字段 | JSON类型 | 必返 | 可空 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | string(int64) | 是 | 否 | 导入批次ID的十进制字符串 |
| `status` | string | 是 | 否 | 第12节批次状态 |
| `currentStage` | string | 是 | 是 | 第12节阶段；`uploaded`时为`null` |
| `progressPercent` | number | 是 | 否 | 0至100，最多两位小数，按第13.1节计算 |
| `totalCount` | integer | 是 | 否 | 派生值，等于`validCount + failedCount`，不新增数据库列 |
| `validCount` | integer | 是 | 否 | 第13节定义的有效记录数 |
| `warningCount` | integer | 是 | 否 | 第13节定义的warning问题条数 |
| `failedCount` | integer | 是 | 否 | 第13节定义的失败行数 |
| `startedTime` | string(date-time) | 是 | 是 | 预检开始时间；`uploaded`时为`null` |
| `finishedTime` | string(date-time) | 是 | 是 | `waiting_confirm/failed`时非空，其他状态为`null` |
| `failureTraceId` | string | 是 | 是 | 仅`failed`时非空 |

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "id": "10001",
    "status": "validating",
    "currentStage": "validate_tree",
    "progressPercent": 76.50,
    "totalCount": 765,
    "validCount": 750,
    "warningCount": 3,
    "failedCount": 15,
    "startedTime": "2026-07-30T10:31:00+08:00",
    "finishedTime": null,
    "failureTraceId": null
  }
}
```

`failureTraceId` 仅在 `status=failed` 时非空。前端在 `uploaded/parsing/validating` 时继续轮询，在 `waiting_confirm/failed` 时停止轮询。

本接口可能返回：`IMPORT_FORBIDDEN`、`IMPORT_BATCH_NOT_FOUND`、`IMPORT_SYSTEM_FAILURE`。

## 11. 接口四：分页查询问题

```http
GET /api/admin/imports/10001/issues?pageNum=1&pageSize=20&severity=error&orderByColumn=lineNo&isAsc=asc
```

| 参数 | 类型 | 默认值 | 规则 |
| --- | --- | --- | --- |
| `pageNum` | integer | 1 | 最小1 |
| `pageSize` | integer | 20 | 1至100 |
| `severity` | string | 无 | `warning/error` |
| `issueCode` | string | 无 | 精确匹配 |
| `orderByColumn` | string | `lineNo` | `lineNo/severity/issueCode/createTime` |
| `isAsc` | string | `asc` | `asc/desc/ascending/descending` |

排序字段必须映射到服务端白名单，不能把前端参数直接拼接为 SQL。

PostgreSQL排序映射固定为：

- `lineNo`：优先使用关联记录的`source_line_no`；`import_record_id=NULL`时，从严格匹配`$line[n]`的`field_path`提取整数；
- `severity`：`error`排在`warning`前；
- `issueCode`：映射到`cm_import_issue.issue_code`；
- `createTime`：映射到`cm_import_issue.create_time`；
- 所有排序最后追加`cm_import_issue.id`同方向排序，保证分页稳定。

非法JSON行号提取必须使用参数固定的PostgreSQL表达式或Mapper中预定义SQL片段，不能把请求内容带入正则或SQL。无法从历史`field_path`提取行号的数据排在有行号数据之后。

返回类型：`R<PageResult<ImportIssueVo>>`。复用当前 `PageResult<T>`，响应只包含 `rows/total`。

`ImportIssueVo`字段固定为：

| 字段 | JSON类型 | 必返 | 可空 | 说明 |
| --- | --- | --- | --- | --- |
| `lineNo` | integer | 是 | 否 | 原始JSONL物理行号，从1开始 |
| `sourceKey` | string | 是 | 是 | 合法JSON对象可提取时返回；非法JSON为`null` |
| `fieldPath` | string | 是 | 是 | 字段路径或`$line[n]`；没有具体路径时为`null` |
| `severity` | string | 是 | 否 | `warning/error` |
| `issueCode` | string | 是 | 否 | 第14.2节稳定`KP_*`问题码 |
| `message` | string | 是 | 否 | 脱敏中文说明 |
| `createTime` | string(date-time) | 是 | 否 | 问题创建时间，ISO 8601，带时区偏移 |

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "rows": [
      {
        "lineNo": 12,
        "sourceKey": null,
        "fieldPath": "$line[12]",
        "severity": "error",
        "issueCode": "KP_JSON_INVALID",
```

问题接口禁止返回 `raw_record`、完整原始行、对象键、文件哈希、行哈希、Token、Cookie、对象存储凭据和异常堆栈。

本接口可能返回：`IMPORT_FORBIDDEN`、`IMPORT_BATCH_NOT_FOUND`、`IMPORT_SYSTEM_FAILURE`。分页或筛选参数非法时返回`IMPORT_CONTEXT_INVALID`，并在`fieldErrors`中定位具体参数。

## 12. 状态和阶段

状态机固定为：

```text
uploaded -> parsing -> validating -> waiting_confirm
   |           |           |
   +-----------+-----------+-> failed
```

`failed`是批次级终态。文件读取失败、对象存储读取失败、数据库失败、已领取任务的Worker异常或任务达到最大重试次数时，可以使`parsing/validating`进入`failed`。创建预检任务的事务失败时批次保持`uploaded`，不产生无人处理的`parsing`状态。行级校验问题不能触发该状态。

| 状态 | 含义 | 是否继续轮询 |
| --- | --- | --- |
| `uploaded` | 文件和批次已创建，尚未触发预检 | 是 |
| `parsing` | 流式读取 JSONL，只为合法 JSON 创建记录 | 是 |
| `validating` | 校验字段、映射、重复和树关系 | 是 |
| `waiting_confirm` | 预检完整结束，可以存在行级错误 | 否 |
| `failed` | 文件、存储、数据库或任务级故障 | 否 |

`parsing`表示`knowledge_point_precheck`任务已经持久化为待执行或正在执行，不表示内存线程一定已经启动。`currentStage` 固定为：

```text
read_jsonl
validate_schema
validate_mapping
validate_tree
finalize_counts
```

行级 error 不会使批次进入 `failed`。只要预检流程完整执行并形成可查询问题，批次进入 `waiting_confirm`。

## 13. 统计口径

| 字段 | 口径 |
| --- | --- |
| `validCount` | 没有任何 error 的记录数，包含只有 warning 的记录 |
| `failedCount` | 存在至少一个 error 的记录数，加非法 JSON 行数 |
| `warningCount` | warning 问题条数，不是记录数 |
| `totalCount` | `validCount + failedCount` |

示例：

- 一条记录有3个 error，`failedCount` 只增加1；
- 一条记录有3个 warning，`warningCount` 增加3；
- 一条记录只有 warning，仍计入 `validCount`；
- 非法 JSON 增加 `failedCount`，但不创建 `cm_import_record`；
- `progressPercent` 表示任务执行进度，不能根据正确率推算。

进入 `waiting_confirm` 前，服务端必须按记录和问题重新核对最终统计。

### 13.1 进度百分比

进度必须单调不减，保留两位小数，并按以下区间计算：

| 状态/阶段 | 百分比区间 | 计算口径 |
| --- | --- | --- |
| `uploaded` | 0 | 固定为0 |
| `read_jsonl` | 0～30 | `已读取文件字节数 / 文件总字节数 * 30` |
| `validate_schema` | 30～50 | 按已校验合法JSON记录数占合法JSON记录总数线性计算 |
| `validate_mapping` | 50～65 | 按已校验合法JSON记录数占合法JSON记录总数线性计算 |
| `validate_tree` | 65～90 | 按已完成树校验记录数占合法JSON记录总数线性计算 |
| `finalize_counts` | 90～99 | 统计复核开始为90，全部复核完成为99 |
| `waiting_confirm` | 100 | 固定为100 |
| `failed` | 保留故障前最后值 | 不归零、不强制写100 |

分母为0时，阶段开始使用区间下界，阶段成功结束直接写区间上界。数据库更新必须使用`max(原进度, 新进度)`语义，防止并发回写造成进度倒退。

## 15. 幂等、存储和异步

### 15.1 幂等

创建批次的规范化载荷固定包含：

```text
importType
syllabusVersionId
按subjectNo升序排列的subjectMappings
templateVersion
服务端文件SHA-256
```

- 相同 `X-Request-Id`、相同载荷：返回首次批次，`reused=true`；
- 相同请求号、不同载荷：返回 `IMPORT_REQUEST_ID_CONFLICT`；
- Redis 锁只用于减少并发竞争，`cm_import_batch.request_id`的全局唯一约束是导入批次的最终保证；
- `@RepeatSubmit`不能替代上述规则。

首次失败是否占用请求号按下表处理：

| 阶段 | 是否存在批次/幂等记录 | 同一请求号再次到达 | 处理 |
| --- | --- | --- | --- |
| 请求、上下文或文件级校验拒绝 | 否 | 按新请求重新校验 | 不承诺重放首次错误；修正输入后可使用原请求号 |
| 已接收字节并计算哈希，但首次数据库事务未提交时发生系统故障 | 否 | 按新请求重新处理 | 受控清理孤儿对象；不得假称可返回首次失败 |
| 已提交批次 | 是 | 相同载荷返回原批次 | 不创建第二批次 |
| 已提交批次后发生对象或任务级系统故障 | 是 | 返回已持久化的失败响应 | 不创建第二批次；不同载荷返回409 |

### 15.2 对象存储补偿

MinIO与数据库不构成同一事务，创建批次按以下顺序执行：

1. 服务端流式接收文件到私有临时对象，并计算文件SHA-256；
2. 文件级校验失败时立即删除临时对象；删除失败时写入`import_object_cleanup`任务，且不创建批次或幂等记录；
3. 文件级校验通过后生成批次ID和最终私有对象键，在移动前写入一条以批次ID为业务键的清理任务，任务载荷仅包含对象键、预期SHA-256和清理原因；
4. 将临时对象移动到最终对象键，并重新确认对象存在且哈希一致；移动失败时只保留清理任务，返回`IMPORT_SYSTEM_FAILURE`；
5. 在一个数据库事务中创建或锁定`cm_idempotency_record`，创建`cm_import_batch`并绑定已验证的最终对象，再将对应清理任务取消；
6. 事务冲突、回滚或发现同请求已有批次时，保留或重新激活清理任务删除本次对象；不得覆盖既有批次对象；
7. 清理任务按`cm_async_job`退避重试；达到上限后保留失败记录并触发运维告警，任何未绑定批次的对象都不得被预检任务读取。

数据库只保存私有对象键、服务端哈希和元数据；不使用会写`sys_oss`并返回临时URL的通用上传接口。对象键、文件哈希和任务载荷不通过普通API、问题消息或日志返回。

### 15.3 预检异步和任务恢复

- 使用独立 Spring Worker Bean，避免 `@Async` 自调用失效；
- `POST /validate`在一个事务内完成`uploaded -> parsing`条件更新和`knowledge_point_precheck`任务插入，任务业务键固定为批次ID；二者任一失败均回滚；
- 任务分发器只领取已提交的`queued`任务。领取、重试和终态更新使用`cm_async_job`条件更新；任务达到最大重试次数时，以条件更新将对应批次从`parsing/validating`置为`failed`；
- Worker 的`parsing -> validating -> waiting_confirm/failed`迁移同样使用条件更新，迟到任务不得覆盖终态；
- 进度更新使用`max(原进度, 新进度)`语义，防止并发回写倒退；
- Worker 捕获异常并将批次置为 `failed`，记录安全摘要和 `traceId`；
- JVM重启后，`queued`任务由分发器继续领取；进程中断时，超过租约的`running`任务回到`queued`并增加尝试次数。租约时长、心跳间隔和自动重试参数属于P1调优项。

## 16. 非法 JSON 的预检兼容处理

当第`n`行不能解析为JSON对象，或该行超过1MiB限制时，不创建原始记录，只创建可定位问题：

```text
cm_import_record：不创建
cm_import_issue.import_record_id：NULL
cm_import_issue.issue_code：KP_JSON_INVALID、KP_JSON_DUPLICATE_KEY或KP_JSON_LINE_TOO_LARGE
cm_import_issue.severity：error
cm_import_issue.field_path：$line[n]
API.lineNo：n
API.sourceKey：NULL
```

处理规则：

1. 不向非空 `raw_record jsonb` 写入伪对象或原始字符串；
2. `message`只写“第n行不是合法JSON”或“第n行超过单行大小限制”等脱敏摘要，不回显上传字段值；
3. 数据库、普通日志和 API 均不保存或输出完整原始行；
4. 原始行 SHA-256 只用于受限安全日志关联，不通过普通接口返回；
5. 非法行计入 `failedCount`，但不计入合法记录数量。

### 16.1 后续设计债务

- 为 `cm_import_issue` 增加 `source_line_no integer`；
- 评审是否增加 `source_line_hash varchar(64)`，并定义访问权限和保留期限；
- 新字段落地后优先读取独立行号，同时兼容历史 `$line[n]`；
- 禁止为了消除债务而给非法 JSON 创建虚假的 `cm_import_record`。

## 17. 安全和零写入复核

技术复核必须逐项确认：

- 服务端重新计算文件 SHA-256，不信任前端哈希；
- 使用流式读取，不一次性加载完整 JSONL；
- 先解析为 `JsonNode`，再执行13字段严格白名单；
- 解析器必须在构造`JsonNode`前拒绝重复字段名；
- 日志、问题`message`和普通错误响应不输出文件正文、原始行、上传字段值、Token、Cookie、Authorization、对象键、文件哈希和对象存储凭据；问题列表中的`sourceKey`仅在其满足本规范固定格式时作为结构定位符返回，其他上传字段均不得返回；
- `KP_TREE_CYCLE`仅返回行号、字段路径和“该行形成循环引用”的通用消息，不返回`syllabus_number`、循环路径或标题；
- 四接口执行权限和数据范围检查；
- 排序字段经过白名单映射；
- 系统故障能通过 `traceId` 定位；
- 预检服务不调用 `cm_knowledge_point` 写服务，也不得直接对该表执行`INSERT`、`UPDATE`或`DELETE`；
- 预检前后正式知识点的主键集合、数量、内容摘要和更新时间不变。

出现数据污染、重复批次、权限泄露、统计错误或原始数据泄露时，预检直接判定不通过。
