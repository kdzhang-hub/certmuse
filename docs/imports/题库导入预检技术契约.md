## 1. 范围

本契约规定题库包从上传到发布的处理顺序、数据库写入边界、错误码和验收证据。题目与映射文件的字段定义以《题库 JSONL 导入规范 V1》为准。

本次冻结覆盖格式、数据基线、分流规则和数据库边界。题库导入服务、管理端页面及评分点批次入口尚未据此实现，不能把文档状态解释为接口已经上线。

| --- | --- | --- |
| 题目 JSONL | 规则已冻结，原件待核验 | 字段、类型和 4,658 条来源记录固定；原始字节哈希待写入冻结清单 |
| 答案 | 已冻结 | 单选答案全部有效；80 道来源主观题的 `null` 作为明确值保留 |
| 知识点映射 | 规则已冻结，原件待核验 | 原始映射不改写；4,528 条知识点合规，178 条按固定规则进入隔离草稿 |
| 评分点 | 格式已冻结，数据为空 | `question_scoring_point/1.0` 不再改字段；当前没有评分点文件和评分点记录 |

## 2. 冻结基线

[题库冻结清单 V1](题库冻结清单.md)记录文件哈希、行数、图片集合哈希和统计结果。当前统计基线必须满足：

| 指标 | 冻结值 |
| --- | ---: |
| 来源题目 | 4,658 |
| 映射记录 | 4,658 |
| 知识点关联 | 4,923 |
| 图片文件 | 714 |
| 跨科目来源题 | 47 |
| 有知识点的科目副本 | 4,696 |
| 无知识点草稿 | 10 |
| 不合规知识点草稿 | 168 |
| 隔离草稿合计 | 178 |
| 知识点合规题目记录 | 4,528 |
| 数据库题目记录总数 | 4,706 |
| 来源主观题空答案 | 80 |
| 评分点数据 | 0 |

基础文件和图片原件不在本仓库中。冻结清单的哈希字段完成计算和复核前，不得启用该数据集的上传、预检或正式导入；导入内容与已复核清单不匹配时也必须停止。

图片集合哈希使用 `sha256-path-size-content-sha256/1.0`。递归读取 `images/` 中的普通文件，以 ZIP 根目录为基准生成使用 `/` 的相对路径，按路径的 UTF-8 字节升序排列。每个文件生成 `相对路径 + NUL + 十进制字节数 + NUL + 文件 SHA-256 大写十六进制 + LF`，再对全部记录的 UTF-8 字节串计算 SHA-256。路径、大小或内容任一变化都会改变集合哈希。

## 3. 批次模型

外部上传对象是完整 ZIP 包，最大 100 MiB。预检通过后，系统按现有数据库约束登记四个批次：一个 `question_knowledge` 批次和科目 1、2、3 各一个 `question` 批次。题目批次填写对应的 `exam_subject_id`，映射批次填写 `syllabus_version_id`。每个批次的 `source_file_path`、`source_file_hash` 和 `source_file_size` 记录实际组件文件，不记录 ZIP；题目文件约 7.2 MB，映射文件约 0.5 MB，均不超过数据库现有的 10 MiB 上限。图片按文件写入对象存储，不作为 `cm_import_batch` 的单个源文件。

四个批次的 `parse_config` 都写入相同的 `dataset_code`、两个基础文件 SHA-256、图片集合 SHA-256 和逻辑导入组标识。三个题目批次的 `template_version` 使用 `question/1.0`，映射批次使用 `question_knowledge/1.0`；四个批次的 `parser_version` 均使用 `question-bank-import/1.0`。`question_bank_pair/1.0` 只标识外部 ZIP 上传包，不写入组件批次的 `template_version`。这样保留现有 `cm_question.exam_subject_id NOT NULL`、题目批次单科目上下文和 10 MiB 文件限制，不需要数据库迁移。

批次状态按下列顺序推进：

```text
uploaded -> parsing -> validating -> waiting_confirm -> importing -> completed
```

任何解析或校验错误都使批次进入 `failed`，不能确认导入。正式写入发生未预期错误时回滚数据库事务，批次进入 `failed`。不得用 `partial_failed` 表示本冻结批次的正常结果。

每个实际生成的科目副本在对应题目批次中生成一条 `cm_import_record`：

- `source_line_no` 使用 `questions.jsonl` 行号；
- `source_key` 使用 `question-bank-v1:{qid}:{subject_no}`；
- `raw_record` 同时保存题目对象和映射对象；
- `raw_hash` 对两个原始行按固定顺序拼接后计算 SHA-256；
- `result_data` 保存生成的题目 ID、修订 ID、科目编号和修订状态，不保存完整题目内容。

`raw_record` 使用 `question_import_record/1.0`，顶层固定包含 `schema_version`、`question` 和 `knowledge_mapping`。`result_data` 使用 `question_import_result/1.0`，顶层固定包含 `schema_version`、`question_id`、`question_revision_id`、`subject_no` 和 `revision_status`，以满足现有 JSONB 约束。

## 4. 预检顺序

预检按以下顺序执行，前一步无效时跳过依赖它的后续推断：

1. 校验 ZIP、路径穿越、文件名、文件数量和解压上限。
2. 校验冻结清单、基础文件 SHA-256 与图片集合 SHA-256。
3. 按物理行校验 UTF-8、BOM、大小、重复字段和 JSON 根节点。
4. 校验字段白名单、类型、长度、枚举和单题答案。
5. 校验题目键一一对应和文件内唯一性。
6. 校验图片引用与实际图片集合完全相等。
7. 校验 `subject_no + code`、科目映射、知识点状态和叶子属性，并标记需要进入草稿的科目分组。
8. 计算多科目拆分结果、稳定来源键、内容哈希和目标记录数。
9. 按 `source_key` 检查已完成批次中的成功导入记录。
10. 汇总问题并进入 `waiting_confirm`。

相同 `source_key` 已经成功导入且内容哈希一致时，该目标记录按幂等成功处理；内容哈希不一致时返回冲突，不能覆盖原题目或修订。新题目的 `question_code` 由应用独立生成，唯一冲突时重新生成。

## 5. 正式写入

确认导入前，服务端必须再次校验批次状态、两个基础文件 SHA-256、图片集合 SHA-256 和操作者权限。图片先写入临时 OSS 前缀，全部成功后再开始数据库事务。

数据库事务内按来源题处理：

1. 无知识点题按题型确定科目，生成有科目的 `cm_question` 和 `draft` 修订，不写知识点关系。`CHOICE`、`CASE`、`ESSAY` 分别使用科目 1、2、3；当前 10 道均进入科目 1 草稿。
2. 有知识点题按不同 `subject_no` 生成题目记录，`evidence_group_key` 固定为 `question-bank-v1:{qid}:{subject_no}`，不得跨科目共用。
3. 科目分组包含未找到、停用、已删除或非叶子知识点时，写入有科目的 `draft` 修订，不写该分组的任何知识点关系。
4. 其余题目写入题目修订、选项、图片和本科目知识点关系。
5. 本科目只有一个有效知识点时可将该关系标记为 `primary`；有多个知识点时关系角色留空。新建映射的状态统一写为 `unclassified`，来源 `tag_status` 只保存在原始记录中，不能直接写为数据库 `reviewed`。
6. `unclassified` 来源记录不写知识点关系；其他来源映射在平台完成主次复核后才能改为 `reviewed`。
7. 所有新修订固定写为 `draft`，只生成 `created` 事件。导入过程不得代替提交、审核或发布操作。

整个批次使用一个数据库事务。失败时回滚全部目标表写入，并清理本批次临时 OSS 对象。事务提交后将临时图片提升为正式对象；提升失败时记录可重试补偿任务，不把不存在的图片路径返回给学员端。

预期统计如下：

```text
valid_count = 4658
failed_count = 0
generated_count = 4706
```

`warning_count` 按实际问题条数统计。尚未完成平台确认的映射、需要指定主知识点的多知识点映射、无知识点草稿和不合规知识点草稿均生成 warning，但不会被计入失败记录。导入生成的修订均为草稿；其中 178 条是知识点问题导致的隔离草稿，不属于部分失败。

## 6. 发布门槛

题目修订离开 `draft` 前必须同时满足：

- `cm_question.exam_subject_id` 非空；
- 当前修订至少有一个 `cm_question_knowledge`；
- `knowledge_mapping_status = 'reviewed'`；
- 所有关联知识点属于同一科目；
- 所有关联知识点为有效叶子；
- `CHOICE` 有合法选项和标准答案；
- 图片引用存在正式 OSS 对象。

现有数据库强制科目非空和题目知识点同科目，但不会阻止没有知识点的修订离开草稿。发布服务必须校验本节全部条件，学员查询固定只读取 `published` 修订。以后如果增加数据库触发器，只能作为额外防护，不能改变这里冻结的状态规则。

## 7. 评分点补充

当前基线没有评分点文件，评分点数据条数冻结为 0。`question_scoring_point/1.0` 冻结文件结构、校验和新修订写入规则。后续评分点补充沿用 `import_type = 'question'`，使用 `template_version = 'question_scoring_point/1.0'` 区分处理模式，并按目标题目的考试科目拆分批次，不增加数据库导入类型。实现时必须解析唯一 `source_key`，验证题型、总分、评分点分值和叶子知识点，并创建新修订，不能直接修改已发布修订。

主观题在没有评分点时只允许不计分的内容展示；答案非空时可以展示参考答案。此类题不进入正式计分、作答结算或人物画像。评分点修订发布后，新的学习会话才能使用它；旧会话继续引用创建时的快照。

评分点知识点可以跨考试科目，但必须属于批次指定的考纲版本，并且是启用、未删除的叶子知识点。这一规则沿用现有 `cm_scoring_point_knowledge` 设计，不增加科目字段。

| `QB_UNKNOWN_FIELD` | error | 出现模板未定义字段 |
| `QB_REQUIRED_FIELD_MISSING` | error | 缺少必填字段 |
| `QB_FIELD_TYPE_INVALID` | error | 字段类型错误 |

问题去重键固定为 `batch_id + import_record_id + issue_code + field_path`。

## 9. 幂等、并发和恢复

- 创建批次和确认导入分别使用独立请求 ID。
- 同一请求 ID 和相同载荷返回原结果；相同请求 ID 和不同载荷返回冲突。
- 正式导入按 `dataset_code + 两个基础文件 SHA-256 + 图片集合 SHA-256` 加分布式锁，避免两个批次同时导入相同来源记录。
- `question_code`、修订号、选项标签、知识点关系和评分点编码继续依赖现有数据库唯一约束。
- 失败重试创建新批次并填写 `retry_from_batch_id`，旧批次和原始记录不覆盖。

## 10. 验收证据

契约冻结完成必须同时提供：

1. 清单哈希、行数和统计结果复核通过。
2. 当前数据库表、字段、外键、批次上下文和文件上限与文档逐项核对通过，不要求新增迁移。
3. 4,528 条记录通过知识点合规校验，178 条记录确定性进入隔离草稿；所有新修订仍从 `draft` 开始并按发布流程流转。
4. 80 道来源主观题的空答案和评分点数据为 0 的现状写入清单。
5. 规范、预检契约、清单和数据库设计使用相同字段、数量与状态语义。

导入服务实现后还必须补齐成功、失败、跨科目、草稿、幂等和篡改检测测试。管理端与学员端实现后还必须验证草稿隔离，以及无评分点主观题不产生评分或画像证据。这些是后续实现验收项，不属于本次格式冻结已经完成的功能。
